% ============================================================
\chapter{Introduction}
% ============================================================

Flash-sale workloads send a short burst of concurrent orders toward a small amount
of inventory. A backend must preserve stock correctness while processing requests
quickly, and must control work when the incoming rate exceeds available capacity.

This project compares a synchronous PostgreSQL inventory baseline with an
asynchronous design using RabbitMQ and an atomic Redis Lua reservation. It evaluates
correctness, request and completion latency, throughput, overload response, and the
effect of running multiple consumers on one host. The research question, boundaries,
and experiment controls are recorded in
\texttt{docs/00-scope-lock.md} and \texttt{docs/experiment-protocol.md}.

% ============================================================
\chapter{Problem Statement}
\label{sec:problem}
% ============================================================

With finite stock, a read-check-write sequence can let concurrent requests reserve
the same remaining unit. A conditional atomic update can prevent that race, but
contention may affect latency and throughput. In an asynchronous design, separate
services also have to handle partial failures, redelivered messages, and traffic
above capacity without losing track of accepted orders.

This project asks how C0 (a deliberately unsafe demonstration), C1 (synchronous
PostgreSQL atomic update), and C2 (RabbitMQ with Redis Lua reservation) behave under
matched workloads. C3 adds load shedding; C4 compares 1, 2, and 4 Inventory Service
replicas on the same EC2 host. C0 is only a race-condition demonstration; C1 is the
correctness and performance baseline. The study measures the trade-offs rather than
assuming that a relational database or a microservices architecture is inherently
faster or safer.

% ============================================================
\chapter{Objectives}
% ============================================================

\begin{enumerate}
  \item Compare C0 and C1 with the asynchronous C2 design under equivalent
    conditions; evaluate C3 overload controls and C4 same-host replica counts.
  \item Check the inventory rules in \texttt{docs/inventory-invariants.md}, including
    no negative stock, no oversell, one reservation per order, and no duplicate
    side effects on redelivery.
  \item Measure request acceptance and end-to-end completion separately, alongside
    latency percentiles, throughput, rejection, queue, resource, retry, and DLQ
    measures.
  \item Determine whether accepted orders reach a terminal state or are surfaced by
    reconciliation, and limit conclusions to the tested hardware, workloads, and
    failure scenarios.
\end{enumerate}

% ============================================================
\chapter{Scope}
% ============================================================

See \texttt{docs/00-scope-lock.md} for the research question and scope. The system
includes Order Service, Inventory Service, a deterministic Process Worker,
PostgreSQL schemas owned by each service, Redis Lua stock reservation, RabbitMQ,
and the Nginx, application and queue load-shedding controls of C3. The backend target
is one AWS EC2 host; JMeter runs on a separate machine. C4 varies Inventory Service
replicas as 1, 2, and 4 processes or containers on that same host.

The study excludes a frontend, authentication and authorization, real payment
processing, payment-failure compensation, multi-node scaling, clusters, and
multi-region deployment. It does not claim that one-host replication represents
multi-node horizontal scaling.

% ============================================================
\chapter{Limitations}
% ============================================================

The results have the following limits:

\begin{itemize}
  \item PostgreSQL, Redis, and RabbitMQ each run as a single instance. The project
    does not evaluate cluster failover, infrastructure node loss, or multi-region
    network effects.
  \item The Process Worker uses a deterministic delay and successful result; the
    study does not characterize real downstream failure rates or compensation.
  \item Replica experiments use processes or containers on one EC2 host. Shared CPU,
    memory, and I/O contention limit how far their results can be generalized.
  \item Load-shedding thresholds and the reservation-attempt target are specific to
    the recorded hardware and workload; they are not universal capacity guarantees.
  \item Authentication and authorization are out of scope. The order-status API
    therefore must not be presented as production-secure, and a GUID is not a
    substitute for an authorization check.
\end{itemize}

\chapter{System Requirements}
% ============================================================

Requirements below follow the teacher brief (\texttt{docs/teacher-brief.md},

\section{Functional Requirements}
\begin{enumerate}
  \item \textbf{FR-1 Order intake.} Accept and persist an order for one product
    and return its order ID as soon as the request is accepted, in state
    \texttt{PendingStock}, without waiting for inventory.
  \item \textbf{FR-2 Status polling.} Let the client poll an order's current
    state until it reaches a terminal state or times out.
  \item \textbf{FR-3 Atomic reservation.} Check and reserve inventory atomically
    (Redis Lua in C2--C4; conditional atomic update in PostgreSQL for C1), so
    concurrent requests can never reserve more than the available stock.
  \item \textbf{FR-4 Status from reservation result.} Move the order to
    \texttt{Confirmed} or \texttt{Rejected} from the \texttt{StockReserved} or
    \texttt{StockRejected} event.
  \item \textbf{FR-5 Downstream processing.} A Process Worker consumes
    \texttt{StockReserved}, simulates downstream work with a deterministic
    delay and a successful result, and uses the order ID as its idempotency key.
  \item \textbf{FR-6 Messaging.} Publish and consume events through RabbitMQ,
    with publisher confirms.
  \item \textbf{FR-7 Transactional Outbox.} Every producer writes its business
    change and its outgoing event in one local transaction; a publisher retries
    until the broker confirms.
  \item \textbf{FR-8 Inbox.} Every consumer records each message ID under a
    unique constraint, in the same transaction as its business change, so a
    redelivered message has no second effect.
  \item \textbf{FR-9 Retry and DLQ.} Retry transient failures a bounded number
    of times; move poison or exhausted messages to a dead-letter queue.
  \item \textbf{FR-10 Reconciliation.} A periodic job finds orders stuck in a
    non-terminal state too long. It is a safety net, not a replacement for the
    Outbox, retry or DLQ.
  \item \textbf{FR-11 Warm-up gate.} Load inventory into Redis before the sale
    and open the sale only after warm-up is complete and confirmed.
  \item \textbf{FR-12 Stage timestamps and history.} Record the state and a
    timestamp at each processing stage, including a state-transition history.
  \item \textbf{FR-13 Client and message deduplication.} Reject duplicate
    client submissions (Idempotency-Key) and ignore duplicate or invalid
    events without repeating a state transition.
  \item \textbf{FR-14 Load shedding.} When configured limits are reached
    (Nginx rate limit, application concurrency limit, bounded RabbitMQ queue),
    reject new work early with a suitable status code, before an order is
    created. Never return ``accepted'' for work the system cannot guarantee to
    continue. Evaluated in C3.
\end{enumerate}

\section{Non-Functional Requirements}
\begin{itemize}
  \item \textbf{Consistency.} In every tested workload and failure scenario:
    inventory never goes negative; successful reservations never exceed the
    initial inventory; an order is reserved at most once; a duplicate message
    causes no duplicate side effect. Checked after each run by the four
    invariants in \texttt{docs/inventory-invariants.md}; a failed or
    inconclusive run is reported, never counted as a pass.
  \item \textbf{Performance.} Evaluate at several load levels. Every experiment
    records the EC2 configuration, virtual users and request rate, test
    duration, number of products, initial inventory, number of consumer
    replicas, payload size, and the PostgreSQL, Redis and RabbitMQ
    configuration. The initial target is about 2,000 reservation attempts per
    second on the chosen hardware; this is an experimental target, not a
    hardware-independent guarantee. API throughput and business-completion
    throughput are reported separately.
  \item \textbf{Resilience.} Under overload, reject part of the load in a
    controlled way instead of accepting without limit. After load drops, the
    backlog must drain and the system must return to a stable state without a
    full restart.
  \item \textbf{Observability.} Every order can be traced by correlation ID,
    order ID, message ID, current status and state-transition history, plus
    four timestamps: request acceptance, event publication, stock processing
    and completion.
  \item \textbf{Liveness.} Every accepted order reaches a terminal state or is
    surfaced by reconciliation; order counts by state must reconcile with the
    number of accepted requests.
  \item \textbf{Replication scope.} Compare 1, 2 and 4 Inventory consumer
    replicas on the same EC2 host; do not claim multi-node scalability from
    these runs.
  \item \textbf{Reproducibility.} Reset, seed and warm up before each run;
    repeat each configuration 3--5 times; report percentiles, median and
    run-to-run variation, not only averages.
\end{itemize}

\chapter{Technology Selection}
% ============================================================

\begin{description}
  \item[ABP Framework 10.6 on .NET 10] Required by the brief. Used for module
    wiring, EF Core integration and hosting, from the \texttt{app-nolayers}
    template to keep each service's codebase proportional to its size. ABP's
    own RabbitMQ event bus (\texttt{Volo.Abp.EventBus.RabbitMQ}) is
    \emph{not} used: messaging goes through \texttt{RabbitMQ.Client} 7.1.2
    directly, because the design needs per-message publisher confirms and plain
    (non-enveloped) JSON messages per event, which the implementation chapters
    explain.
  \item[PostgreSQL 16] The durable, transactional side (orders, Outbox,
    Inbox). The Transactional Outbox needs the business write and the event
    write to commit in one ACID transaction, so a relational engine is a
    prerequisite. One instance with a schema and a database account per
    service (schema-per-service, not physical isolation). It also hosts the C1
    baseline's conditional atomic update.
  \item[Redis Stack with Lua] Holds available inventory and the
    reservation-level duplicate set. \texttt{scripts/redis/reserve.lua} checks
    idempotency, checks stock, decrements and records the result atomically,
    in one script call. Accessed through \texttt{StackExchange.Redis}.
    RedisInsight (bundled with Redis Stack) is for inspection only.
  \item[RabbitMQ vs.\ Kafka] RabbitMQ fits this workload: routed queues per
    consumer, publisher confirms, bounded retry, dead-lettering and bounded
    queues with an overflow policy for load shedding. Historical log replay,
    Kafka's main advantage, is not part of the research scope.
  \item[Nginx] Entry point and first load-shedding layer (\texttt{limit\_req}
    rate limiting). Sufficient for a single-host deployment without a full API
    gateway.
  \item[Serilog, prometheus-net, Prometheus, Grafana] Structured JSON logs
    carrying correlation, order and message IDs (Serilog), service metrics
    exported by \texttt{prometheus-net}, scraped by Prometheus and viewed in
    Grafana.
  \item[Docker Compose] Runs PostgreSQL, Redis, RabbitMQ, Nginx and the
    monitoring stack identically on a developer machine and the EC2 host.
  \item[Terraform and AWS EC2] The brief requires the system under test on one
    EC2 instance. Terraform (\texttt{infra/terraform/}) creates that host and a
    separate JMeter host reproducibly and removes them again
    (Section~\ref{sec:ec2-deployment}).
  \item[Apache JMeter] Simulates concurrent clients through the order and
    status APIs. It runs on a separate machine so it does not compete with the
    system under test.
\end{description}

\section{Entity-Relationship Diagram}
The data model below is taken from the EF Core models and migrations, the
raw baseline SQL and the role/schema initialisation script, not drawn by hand.
\texttt{docs/erd.md} holds the same diagrams plus a machine-readable manifest,
and \texttt{scripts/verify-erd.ps1} compares that manifest with a live
database. On 2026-10-01 a database built from scratch (role initialisation,
then both services' migrations, then the baseline schema) passed all 29 checks.

\paragraph{Architecture of the data layer.} One PostgreSQL instance holds one
schema per service. Order Service writes \texttt{order\_service}, plus ABP's
module tables in \texttt{public}. Inventory Service writes only
\texttt{inventory\_service}. Each schema is owned by its own login role
(\texttt{order\_service\_user}, \texttt{inventory\_service\_user}). Neither
role can read the other's schema, and only Order Service's role can use
\texttt{public}. The services share data only through RabbitMQ events. There
are no foreign keys: links such as an Outbox row's \texttt{OrderId} are
logical, and they are kept consistent by writing both rows in one local
transaction. Inventory's \texttt{OrderId} refers to an order in another
service's schema, so it could not have a foreign key anyway. In the
asynchronous design, stock is held in Redis, not PostgreSQL:
\texttt{inventory:\{productId\}} stores available units and
\texttt{processed:\{productId\}} stores the ids of orders already reserved.

\paragraph{Unique constraints.} Four unique indexes carry the system's
idempotency guarantees:
\texttt{orders.IdempotencyKey} (one order per client key),
\texttt{processed\_messages.MessageId} in each service schema (each broker
message is applied at most once by each consumer), and
\texttt{inventory\_service.outbox\_events.OrderId} (at most one stock result
per order). Non-unique indexes support trace lookup
(\texttt{orders.CorrelationId}) and Outbox polling (\texttt{Published}).

\paragraph{ABP and the \texttt{public} schema.} Order Service is an ABP
application. Its first migration creates 37 ABP module tables
(\texttt{Abp*}, \texttt{OpenIddict*}) and its EF migration history in
\texttt{public}, all owned by \texttt{order\_service\_user}. They stay in
\texttt{public} because forcing a default schema breaks some ABP modules at
runtime. Inventory Service configures no ABP modules. Its connection string
sets the search path to \texttt{inventory\_service}, so its migration history
is stored there. No business or experiment data lives in \texttt{public}.

\paragraph{Ownership defects found by this check.} Two were found and fixed.
First, on a fresh database the baseline tables were owned by the
\texttt{flashsale} admin account that creates them, so
\texttt{order\_service\_user} had no privileges on them and the C0/C1 runs
would have failed. The baseline schema script now hands them to
\texttt{order\_service\_user}. Second, on a database created before the
per-service accounts existed, both services shared one migration-history table
in \texttt{public}. Once Inventory Service connected with its own search path,
it re-ran its migrations and failed with ``relation already exists''. The
role script now moves Inventory's history rows into
\texttt{inventory\_service}. Both the fresh and the existing-database paths
are checked by \texttt{scripts/verify-environment.ps1}.

Since Week 11, the Order Service schema also holds
\texttt{order\_status\_history}, the per-order transition history required by
the six-state model (Section~\ref{sec:order-state-machine}). Each row records
the from-state, the to-state, the triggering \texttt{MessageId}, the time, and
whether the step was implied. An identity column, \texttt{Seq}, gives the
order in which the rows were written, and every read of the history uses it.

\section{Order State Machine}
\label{sec:order-state-machine}

six named states: \texttt{PendingStock}, \texttt{Confirmed},
\texttt{Rejected}, \texttt{Processing}, \texttt{Completed} and
\texttt{ProcessingFailed}. \texttt{Processing} is reachable through a
dedicated \texttt{OrderProcessingStarted} event published by the Process
Worker when it begins work, followed by \texttt{OrderProcessed} for
\texttt{Processing} $\to$ \texttt{Completed}. \texttt{ProcessingFailed} is
declared but unreachable by design: the scope lock gives the Process Worker
a deterministic, successful outcome only, so no in-scope event produces it
(the success-only interpretation). Reordered or duplicated Worker events are
absorbed by explicit rules (stale events are no-ops; an early
\texttt{OrderProcessed} applies an implied \texttt{Processing} step in the
same transaction), and every transition is appended to an order status
history. Since Week 11 the code implements exactly this model, and the
alignment check compares the transition table with
\texttt{Order.LegalTransitions}. The implementation and its verification are
described in Section~\ref{sec:week11}.

\section{Idempotency, Ordering and Ownership}
\label{sec:design-decisions}
The full definitions, each tied to the code that implements it, are in
\texttt{docs/design-decisions.md} and are checked by
\texttt{scripts/verify-design-decisions.ps1}.

\paragraph{Transport versus business idempotency.} Two \emph{transport} keys
absorb retries of the same request or message. The client's
\texttt{Idempotency-Key} is unique per order, and a reused key with a different
body returns 409. The broker's \texttt{MessageId} is unique per consumer
Inbox and is written in the same transaction as the business change. The
\emph{business} key is \texttt{OrderId}. Redis's per-product set of reserved
order ids and the unique \texttt{OrderId} on Inventory's Outbox guarantee one
deduction and one result per order even when the same fact arrives as a new
message, for example the reconciliation job re-publishing \texttt{OrderPlaced}.

\paragraph{Ordering and replay.} The design does not rely on message order.
Duplicates and events for a state already reached are acknowledged as no-ops.
A conflicting result goes to the service's dead-letter queue. An event that
arrives before its prerequisite is retried, never dropped. Replaying any
message leaves stock, state and Outbox rows unchanged.

\paragraph{Schema ownership.} Each schema has one owner account
(\texttt{order\_service}, plus ABP's \texttt{public} tables, belongs to Order
Service; \texttt{inventory\_service} belongs to Inventory Service). Redis
inventory keys belong to Inventory Service. Services never read each other's
data; facts cross service boundaries only as events.

\paragraph{Redis/PostgreSQL boundary.} Redis decides the reservation
atomically; PostgreSQL then records the result (Outbox row and Inbox row) in
one transaction, and only then is the message acknowledged. If PostgreSQL fails
after Redis has reserved, the message is redelivered. The Lua script answers
\texttt{DUPLICATE} without a second deduction, and the missing result is
written.

\section{Design Rationale}
The project compares a synchronous PostgreSQL conditional update (C1) with an
asynchronous, event-driven design (C2--C4) under the same correctness
invariants. Each mechanism in the asynchronous design was chosen for one
reason:

\begin{itemize}
  \item \textbf{Accept first, decide later (HTTP 201 in \texttt{PendingStock}).}
    It separates the request acceptance rate from the processing rate, so API
    latency and completion latency are measured separately, as the brief
    requires.
  \item \textbf{Redis Lua for the stock decision.} It makes the idempotency
    check, the stock check and the decrement one atomic step in memory,
    instead of a row lock that every buyer of a hot product waits on in C1.
  \item \textbf{Transactional Outbox on both producers.} It removes the
    dual-write problem: an order (or a stock result) and its event commit
    together or not at all, and a publisher retries until the broker confirms.
  \item \textbf{Inbox per consumer.} RabbitMQ delivers at least once; a unique
    \texttt{MessageId} written with the business change makes every effect
    happen at most once.
  \item \textbf{Direct exchange, one queue per consumer.} Order Service and the
    Process Worker each get their own copy of \texttt{StockReserved}; sharing a
    queue would split the messages between them.
  \item \textbf{Schema-per-service on one PostgreSQL instance.} It gives
    ownership and isolation by account at the cost of a single shared server,
    which the brief accepts as a limitation (not physical isolation).
  \item \textbf{Success-only Process Worker.} It keeps the downstream stage
    deterministic, so latency variation in the results comes from the
    architecture rather than from simulated failures. That is why
    \texttt{ProcessingFailed} has no producer.
\end{itemize}

The cost of these choices is complexity: three services, two Outboxes, two
Inboxes, a broker and a cache, compared with one SQL statement in C1. The
Experimental Design and Results chapters quantify what this buys. Replica
results (C4) are limited to processes on one host and do not show multi-node
scaling.

\paragraph{Known gaps in the supported model.} None remain open in the
delivery path. An \texttt{OrderProcessed} that arrives while the order is still
\texttt{PendingStock} used to be dead-lettered. Since Week 9 it is requeued
onto delayed retry queues and applied once the order is \texttt{Confirmed}
(TP-M02). The
database-error defect, where an error was treated as a duplicate and the result

Week 8 (TP-W03).

\subsection{C0 -- the naive baseline (a controlled failure demonstration)}

C0 (\texttt{src/FlashSale.OrderService/Experiments/C0Naive/C0NaiveDemo.cs})
implements the textbook race condition. It reads the current stock, checks it
in application code, then issues a separate, unconditional \texttt{UPDATE}:
two round trips with no locking between them.

\begin{Verbatim}[breaklines=true,breakanywhere=true,fontsize=\footnotesize]
SELECT stock FROM order_service.inventory WHERE product_id = @p;
-- (application code checks: stock > 0 ?)
UPDATE order_service.inventory SET stock = stock - 1 WHERE product_id = @p;
\end{Verbatim}

C0 has no HTTP route. It runs only via \texttt{dotnet run -{}- -{}-run-c0-demo},
which bypasses the ABP host, so no stray request can reach it later in the
project. Five concurrent attempts were fired at a product seeded with
\texttt{stock = 1}. All five wait on a shared start gate so they reach the read
at the same instant, and a 50\,ms pause between read and write widens the race
window so it reproduces on every run. The captured result
(\texttt{20261001T085538Z-c0-race.log}):

\begin{Verbatim}[breaklines=true,breakanywhere=true,fontsize=\footnotesize]
[C0] Seeded 'c0-demo-product' with stock = 1. Firing 5 concurrent naive requests...
[C0] Attempt 4: saw stock=1, Confirmed.
[C0] Attempt 1: saw stock=1, Confirmed.
[C0] Attempt 3: saw stock=1, Confirmed.
[C0] Attempt 2: saw stock=1, Confirmed.
[C0] Attempt 5: saw stock=1, Confirmed.
[C0] Result: 5 of 5 concurrent requests got 'Confirmed' for a product seeded with stock = 1.
[C0] OVER-SOLD: more than one request reserved the same single unit of stock. This is the bug C1 (Step 3.3) fixes.
[C0] Final stock in database: -4 (started at 1).
\end{Verbatim}

All five requests believed they had reserved the single unit, and the
database was left at \(-4\). This is the race condition C1 exists to
eliminate. \texttt{order\_service.inventory} deliberately has no
\texttt{CHECK (stock >= 0)} constraint, so that the bug shows up as overselling
instead of being turned into an unhandled exception.

\subsection{C1 -- the PostgreSQL atomic update}

C1 (\texttt{src/FlashSale.OrderService/Controllers/BaselineOrdersController.cs},
\texttt{POST /api/c1/orders}) replaces the two round trips with one
conditional statement. Its \texttt{WHERE} clause is evaluated by PostgreSQL
against the row's current value while holding the row lock, not against a
value the application read earlier:

\begin{Verbatim}[breaklines=true,breakanywhere=true,fontsize=\footnotesize]
UPDATE order_service.inventory
SET stock = stock - 1
WHERE product_id = @productId AND stock >= 1
RETURNING stock;
\end{Verbatim}

The update and the outcome row in \texttt{baseline\_orders} commit in one
transaction, so the log cannot disagree with the stock. A separate
\texttt{SELECT ... FOR UPDATE} followed by an \texttt{UPDATE} was avoided,
because it re-creates C0's two-statement window unless written very carefully.
C1 lives on its own route; \texttt{/api/orders} belongs to the asynchronous
design, so both configurations stay independently reachable for the Week 13--14
comparison.

\paragraph{Concurrent demand below, equal to and above stock.}
\texttt{scripts/run-baseline.ps1} seeds \texttt{c1-demo-product} with 100
units, starts every request before reading any response, and repeats each
scenario three times:

Scenario & Requests & Confirmed & Rejected & Final stock & HTTP 200 & Verdict \\
\midrule

\paragraph{Connection-pool finding.} The first concurrent prototype never
oversold, but 3--31 of every 150--300 requests failed with HTTP 500

100 connections per service is larger than what PostgreSQL's default
\texttt{max\_connections = 100} leaves for ordinary roles (97), and both
services share that server. The pools are now capped at 60 (Order Service)
and 30 (Inventory Service). These sizes are part of the experiment
configuration and are recorded with every run.

\subsection{Correctness criteria}

The invariants in \texttt{docs/inventory-invariants.md} are applied as
follows. Invariant~1 (\texttt{available\_inventory >= 0}) and Invariant~2
(\texttt{successful\_reservations <= initial\_inventory}) are checked after
every run from the database itself: final stock, and Confirmed rows in
\texttt{baseline\_orders}. C0 violates both under concurrency (final stock
\(-4\), 5 successes for 1 unit). C1 satisfied both in all nine runs. The
captures add two run-level checks: every request receives a decision (HTTP 200
with \texttt{Confirmed} or \texttt{Rejected}, and no errors), and stock is
conserved (final stock = initial stock $-$ Confirmed). Invariants~3 and~4 (one
reservation per order; no duplicate effect from a redelivered message) need an
order identity and message delivery. C0 and C1 have neither, so those
invariants are checked on the asynchronous design from Week 7 onward.

\section{Order Service}
\label{sec:order-service}

Order Service accepts orders, stores them with their \texttt{OrderPlaced}
Outbox row, answers status polling, and applies the stock and processing
results that come back as events. The behaviour below is specified in
\texttt{docs/order-api.md}. Every claim in this section is backed by the
saved Week 5 evidence (\texttt{tests/evidence/20261001T123816Z-*}),
produced from a fresh clone on a brand-new database with Order Service running
under its own database account.

\subsection{API design}

\begin{center}
\begin{tabular}{@{}llp{7.4cm}@{}}
\toprule
Request & Status & Meaning \\
\midrule
\texttt{POST /api/orders} & 201 & New order in \texttt{PendingStock}; body is the order with its id and \texttt{requestAcceptedAt} \\
 & 200 & Same \texttt{Idempotency-Key} and same body: the original order, unchanged \\
 & 400 & Missing or blank key, quantity $\neq 1$, blank product, or malformed JSON; nothing is stored \\
 & 409 & Key already used with a different body; the original order is unchanged \\
\texttt{GET /api/orders/\{id\}} & 200 & Current state and the stage timestamps \\
 & 404 & Unknown order id \\
\bottomrule
\end{tabular}
\end{center}

The request carries \texttt{productId} and \texttt{quantity}. Quantity must
equal 1, because flash-sale orders are single-unit and the reservation script
decrements exactly one unit. A product id with no stock is \emph{not} a
validation error: the order is accepted, and Inventory Service rejects it
asynchronously. The order row and its \texttt{OrderPlaced} Outbox row are
written in one \texttt{SaveChangesAsync} call (Section~\ref{sec:outbox}). All
timestamps are UTC with a \texttt{Z} suffix and are stored at microsecond
precision, so a value read back from PostgreSQL equals the value returned at
creation. Validation runs before any write, so a rejected
request leaves no order and no Outbox row.

\subsection{Idempotency strategy}

The client sends an \texttt{Idempotency-Key} header. It is the
\emph{transport} key for client retries, and is distinct from the broker's
\texttt{MessageId}, which the Inbox uses to absorb redelivered messages
(Section~\ref{sec:design-decisions}). The key is enforced at two levels:

\begin{itemize}
  \item \textbf{Lookup before insert.} A known key with the same body returns
    the original order (200); with a different body it returns 409.
  \item \textbf{Unique index as the final arbiter.} Concurrent requests with
    the same key can all miss the lookup. Only one insert can succeed against
    \texttt{IX\_orders\_IdempotencyKey}. A request that loses this race catches
    exactly that unique violation (PostgreSQL \texttt{23505} on that
    constraint, nothing broader), re-reads the winning order and answers as a
    replay or a conflict.
\end{itemize}

\paragraph{What the Week 5 check found.} Before the fix, quantities 0, 2 and
$-1$ and an empty product id were accepted as orders. When 20 requests with
the same key were sent at once, 6 to 9 of them returned HTTP 500: the unique
index prevented duplicate rows, but the losing requests crashed. A replayed
order also came back with different timestamps (no \texttt{Z}, different
precision). On a fresh clone, an unknown order id returned 500 instead of 404,
because ABP's themed error page needs website files that are not in the
repository; the error page now applies only outside \texttt{/api}.
\texttt{scripts/verify-order-api.ps1} fails 10 checks on the old code.

\paragraph{Result after the fix} (\texttt{20261001T123816Z-order-api.log},
30 of 30 checks):
\begin{itemize}
  \item every validation case returns 400 with no row stored;
  \item a replay returns 200 with a body identical to the first response, and
    a changed body returns 409 with the original order unchanged;
  \item in three rounds of 20 concurrent same-key requests, each round gave
    exactly one 201 and nineteen 200s naming the same order, with one order
    row and one Outbox row;
  \item 200 concurrent requests over 50 keys (4 per key) produced exactly 50
    orders and 50 Outbox rows, one 201 per key, and no key with more than one
    order in the table.
\end{itemize}

\subsection{State management}

\texttt{Entities/Order.cs} implements the state machine as guarded
transitions (\texttt{Order.}\allowbreak\texttt{TransitionTo}). The current code has three legal
transitions: \texttt{PendingStock} $\to$ \texttt{Confirmed}, \texttt{PendingStock}
$\to$ \texttt{Rejected} and \texttt{Confirmed} $\to$ \texttt{Completed}. Every
other pair throws \texttt{InvalidOrderStateTransitionException} and changes
nothing. The adopted six-state model adds \texttt{Processing} in Week 11
(Section~\ref{sec:order-state-machine}).

Result events are applied by \texttt{StockResultProcessor}:

\begin{itemize}
  \item an event for the state the order is already in, with any
    \texttt{MessageId}, is acknowledged without a transition and recorded in
    the Inbox;
  \item an event for a state the order has already passed on
    \texttt{PendingStock} $\to$ \texttt{Confirmed} $\to$ \texttt{Completed}
    (for example \texttt{StockReserved} after \texttt{Completed}) is likewise
    acknowledged. Before Week 5 this case threw and would have been
    dead-lettered; it was found by the Week 5 code check and fixed;
  \item a conflicting event (for example \texttt{StockRejected} after
    \texttt{Confirmed}) throws, nothing is recorded, and the consumer sends it
    to the dead-letter queue;
  \item an event for an unknown order is acknowledged and not recorded.
\end{itemize}

An \texttt{OrderProcessed} that arrives while the order is
\texttt{PendingStock} used to be dead-lettered instead of retried. That was
fixed in Week 9 (TP-M02): it is requeued until the order is
\texttt{Confirmed}.

\subsection{Event Publication Reliability (Week 6) -- the dual-write problem and the Transactional Outbox}
\label{sec:outbox}

\paragraph{The problem.} Once order creation needs to notify another service
(Inventory Service, Week 7) that stock should be reserved, the order write
and the "notify" action become two separate operations against two separate
systems (Postgres and RabbitMQ) that cannot be wrapped in one atomic
transaction the way two SQL statements against the same database can. Naively
sequencing them --- write the order, then publish an event --- exposes two
distinct failure orderings, and a system that only handles one of them is
still broken:

\begin{enumerate}
  \item \textbf{The database commits but the publish fails.} The order now
    exists in \texttt{PendingStock} with no corresponding event ever sent.
    Nothing will ever move it out of \texttt{PendingStock} -- it is silently
    stuck forever, and neither the client nor any operator has any signal
    that anything is wrong.
  \item \textbf{The publish succeeds but the database transaction rolls
    back} (or the process crashes between the two steps). Inventory Service
    now receives an \texttt{OrderPlaced} event for an order that, as far as
    Order Service's own database is concerned, never happened. It may
    reserve real stock against a phantom order that no client will ever be
    able to query or complete.
\end{enumerate}

Both failures share a root cause: two systems that must agree with each
other are being updated as if they were one, with no mechanism enforcing
that they actually end up agreeing.

\paragraph{How the Outbox pattern eliminates both.} Rather than publishing
directly, the order-creation handler writes two rows to \emph{one}
database -- the \texttt{orders} row and a row in \texttt{order\_service.outbox\_events}
recording that an \texttt{OrderPlaced} event needs to be published -- inside
the exact same \texttt{SaveChangesAsync} call
(\texttt{Controllers/}\allowbreak\texttt{OrdersController.cs}). Because both rows are ordinary
rows in the same relational database, Postgres's own transaction guarantee
applies to both simultaneously: either both commit, or neither does. This
directly closes both failure orderings above --- there is no longer a window
where the order exists without a corresponding pending event, or vice versa,
because "the order exists" and "an event needs publishing" have been reduced
to a single fact instead of two facts that could disagree.

This claim is verified directly, not just argued from the pattern's
description, in
\texttt{tests/FlashSale.OrderService.Tests/OutboxAtomicityTests.cs}: a real
SQLite in-memory database (not a mock, and not EF Core's InMemory provider,
which does not enforce relational constraints and so cannot demonstrate a
rollback at all) is made to reject an outbox insert via a genuine primary-key
collision, and the accompanying order insert is confirmed absent afterward
--- the whole transaction rolled back, not just the failing half.

\begin{Verbatim}[breaklines=true,breakanywhere=true,fontsize=\footnotesize]
Failed_outbox_insert_rolls_back_the_order_insert_too: PASS
Order_and_outbox_row_both_commit_in_one_SaveChanges_call: PASS
\end{Verbatim}

Both pass in the saved run \texttt{tests/evidence/}\allowbreak\texttt{20261001T123816Z-unit-tests.trx} (TP-E03).

\paragraph{The same guarantee on the real database.} The unit test uses
SQLite. \texttt{scripts/verify-outbox.ps1} repeats the check on PostgreSQL with
Order Service running under its own account
(\texttt{tests/evidence/20261001T163530Z-outbox.log}, 11 of 11 checks). A normal
request stores exactly one order and one unpublished \texttt{OrderPlaced} row.
With the Outbox \texttt{INSERT} privilege revoked for one request, the request
failed and \emph{no} order row existed afterwards. Once the privilege was
restored, the same key created the order normally.

\paragraph{Outbox workflow.} Writing the Outbox row only records that an
event must be published. A background worker (\texttt{OutboxPublisherWorker})
reads unpublished rows, oldest first, 50 at a time, and publishes each stored
payload. After a full batch that all published it reads the next batch at
once; otherwise it waits 2 seconds (Section~\ref{sec:review-fixes}). The event's \texttt{MessageId} is generated
once, when the Outbox row is written, and stored in the payload, so every
publish attempt for that row sends the same value. A failed attempt is retried
after 1\,s, 2\,s and 4\,s. After that the row stays unpublished and is tried
again on the next poll, indefinitely, until it succeeds. The worker never
crashes the host: a failed tick is logged and the loop continues. In the saved
run, the broker was unreachable when the order was created. The publisher
logged failed attempts and left the payload unchanged. Once a broker came up,
exactly one message arrived, carrying the \texttt{MessageId} stored at commit
time.

\paragraph{Routed confirmation.} A row is marked published only when the
broker has confirmed the message \emph{and} delivered it to every queue that
must receive it (\texttt{docs/outbox.md}). The Week 6 code check found that
this was not true. All three publishers (both Outbox publishers and the Process
Worker's) used \texttt{mandatory: false}, so a message with no matching
binding was silently dropped, yet confirmed and marked published. The
prototype reproduced it: an \texttt{OrderPlaced} published before any queue
was bound was marked published and reached nobody. A second gap is subtler.
\texttt{StockReserved} must reach two queues, Order Service's and the Process
Worker's. If only one was bound, the broker accepted the message while the
Process Worker never saw it.

The fix is the same in all three publishers. The queues each event must
reach are configured per event (\texttt{RequiredSubscriberQueues}:
\texttt{OrderPlaced} $\to$ \texttt{OrderPlaced}; \texttt{StockReserved}
$\to$ \texttt{StockReserved} and \texttt{ProcessWorker.StockReserved};
\texttt{StockRejected} $\to$ \texttt{StockRejected}; \texttt{OrderProcessed}
$\to$ \texttt{OrderProcessed}). Before each publish, every required queue is
checked with a passive declare, which fails if it does not exist, and is then
bound to the exchange; binding is idempotent. The message is published with
\texttt{mandatory: true} on a channel with publisher confirmations and
tracking. \texttt{BasicPublishAsync} then throws on a nack or a return. Any
exception leaves the row unpublished, and an event type with no configured
queues is refused. The consumers still own their queues; the publisher never
creates one.

\paragraph{Failure scenarios.} \texttt{scripts/verify-publication.ps1} runs
each scenario against a throwaway broker
(\texttt{tests/evidence/20261001T163055Z-publication.log}, 18 of 18 checks).
On the old publishers, 8 of its checks fail: the affected messages were
marked published but were never delivered.

\begin{center}
\begin{tabular}{@{}p{4.2cm}p{5.6cm}p{3.4cm}@{}}
\toprule
Scenario & Observed with the fix & Old code \\
\midrule
Valid route & Published; one message in the queue & Same \\
Required queue missing & Row stays unpublished, retries logged; once the queue exists (even unbound) it is delivered once and the binding is restored & Marked published, message lost \\

In every recoverable case the event arrived exactly once after the fault was

was not used for publishing because its options expose no documented way to

\section{Inventory Service}
\label{sec:inventory}

\subsection{Scaffolding}

Inventory Service was scaffolded with a minimal ABP module set (MVC, Autofac,
EntityFrameworkCore.PostgreSql, Swashbuckle, Serilog). It has none of the
identity, account, permission, tenant, setting or OpenIddict modules that
Order Service carries from the default template: the scope lock excludes user
management, authentication and multi-tenancy, so Inventory Service never adds
them. It owns only the \texttt{inventory\_service} schema
(Section~\ref{sec:design-decisions}) and the Redis inventory keys. The
behaviour below is specified in \texttt{docs/inventory.md}. Every result in
this section comes from saved runs on a fresh clone with throwaway Redis,
RabbitMQ and PostgreSQL instances
(\texttt{tests/evidence/20261002T051418Z-inventory.log} and
\texttt{20261002T052244Z-cross-store.log}).

\subsection{Redis key and data design}

\begin{center}
\begin{tabular}{@{}llp{6.8cm}@{}}
\toprule
Key & Type & Meaning \\
\midrule
\texttt{inventory:\{productId\}} & integer & Units still available \\
\texttt{processed:\{productId\}} & set & Order ids that hold a reservation for this product \\
\texttt{sale:open:\{productId\}} & string & Present only after a confirmed warm-up: the sale is open \\
\bottomrule
\end{tabular}
\end{center}

Stock lives only in Redis for the asynchronous design. The per-product
reservation set lets the duplicate check happen inside Redis, in the same
atomic step as the stock change, without consulting PostgreSQL.

\subsection{Lua reservation logic}

\texttt{scripts/redis/reserve.lua} runs as one atomic \texttt{EVAL}: Redis
executes a script without interleaving any other command, so the
check-then-act sequence below cannot race. The C\# side
(\texttt{InventoryReservationService}) only loads the file and passes keys and
arguments; it does not reimplement any of the logic.

\begin{Verbatim}[breaklines=true,breakanywhere=true,fontsize=\footnotesize]
-- KEYS: inventory:{id}, processed:{id}, sale:open:{id}   ARGV: order_id
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return 'DUPLICATE' end
if redis.call('EXISTS', KEYS[3]) == 0 then return 'NOT_OPEN' end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then return 'REJECTED' end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 'RESERVED'
\end{Verbatim}

The duplicate check comes first, so a redelivered order that already holds a
unit is answered \texttt{DUPLICATE} even if the sale has since closed.
Inventory Service maps \texttt{RESERVED} and \texttt{DUPLICATE} to
\texttt{StockReserved}, and \texttt{REJECTED} and \texttt{NOT\_OPEN} to
\texttt{StockRejected}.

\subsection{Inventory warm-up and readiness}

The teacher brief requires that a product opens for sale only after warm-up
is complete \emph{and confirmed}. The Week 7 code check found no such gate.
An un-warmed product was answered \texttt{REJECTED} exactly like a sold-out one,
and nothing recorded whether warm-up had happened.

\texttt{scripts/warm-up.ps1} now handles each product in one atomic Lua step.
It sets the stock, clears the reservation set and sets
\texttt{sale:open:\{productId\}}. It then confirms the product by reading all
three back, prints \texttt{CONFIRMED} per product, and exits non-zero if any
product does not confirm. Until the marker exists, \texttt{reserve.lua}
answers \texttt{NOT\_OPEN} and touches no stock. Re-running warm-up on a product
whose sale is open is refused, because it would restore stock and forget
reservations mid-sale. \texttt{-Force} exists for experiment resets only.

In the saved run, a reservation attempted before warm-up answered
\texttt{NOT\_OPEN} with the stock untouched. Warm-up confirmed all six test
products. A re-run on an open sale was refused (stock stayed at its
post-sale value) and \texttt{-Force} reset it. End to end through the running
Inventory Service, an \texttt{OrderPlaced} for a never-warmed product produced
\texttt{StockRejected} with no Redis key created, and one for a warmed product
produced \texttt{StockReserved}.

\subsection{Inventory invariants under concurrency}

For every product, after any amount of concurrent traffic
(\texttt{docs/inventory.md}):
(1) \texttt{inventory} $\ge 0$;
(2) reservations $\le$ initial stock;
(3) \texttt{inventory} + reservations = initial stock (every unit is either
available or held by exactly one order);
(4) no order id is reserved twice, and a repeated order id is answered
\texttt{DUPLICATE} only if that order already holds a unit.
\texttt{tests/InventoryProbe} drives the real \texttt{reserve.lua} with all
requests in flight at once and checks these per product:

\begin{center}
\begin{tabular}{@{}p{6.2cm}rrrr@{}}
\toprule
Workload & Requests & Reserved & Duplicate & Rejected \\
\midrule
Hot product: 100 units; 300 orders + 100 repeats & 400 & 100 & 52 & 248 \\
4 products: 40/30/20/10 units; demand 50/25/15/10\,\%; 250 orders + 80 repeats & 330 & 100 & 45 & 185 \\
\bottomrule
\end{tabular}

All four invariants held for every product in both workloads. The number of \texttt{RESERVED} answers equalled the

\subsection{OrderPlaced handling and the Redis/PostgreSQL boundary}

\texttt{OrderPlacedConsumer} consumes with manual acknowledgement.
\texttt{OrderPlacedProcessor} checks the Inbox, runs \texttt{reserve.lua},
then writes the result event to its Outbox and the Inbox row in one
PostgreSQL transaction. Only after that commit is the message acknowledged. A
processing error is retried after 1\,s, 2\,s and 4\,s, and then the message is
dead-lettered (\texttt{OrderPlaced.dlq}), never re-queued in a loop.

\paragraph{PostgreSQL failure after the Redis reservation.} Redis and
PostgreSQL cannot share a transaction, so the design makes Redis the decision
and PostgreSQL the record (Section~\ref{sec:design-decisions}). The Week 7 test
(\texttt{scripts/verify-cross-store.ps1}) revokes the Outbox \texttt{INSERT}
right after \texttt{reserve.lua} has run. On the old code the consumer
caught \emph{every} database error as ``a duplicate already recorded this''
and acknowledged the message. The \texttt{StockReserved} result was then lost
for good while the unit stayed reserved, and 5 of the test's 11 checks failed.
The processor now treats only a unique-key violation (PostgreSQL
\texttt{23505}) as a duplicate; any other error propagates to retry and the
dead-letter queue. With the fix (11 of 11 checks):

\begin{itemize}
  \item \textbf{Short outage.} The privilege is restored inside the retry
    window. The retry reached \texttt{reserve.lua} again, got
    \texttt{DUPLICATE}, and wrote \texttt{StockReserved}. Stock was deducted
    exactly once.
  \item \textbf{Long outage.} The retries were exhausted and the message went
    to \texttt{OrderPlaced.dlq} with no Inbox row and no result. After the
    fault was removed, replaying the dead letter rebuilt
    \texttt{StockReserved}, again with exactly one deduction.
\end{itemize}

Order Service's \texttt{StockResultProcessor} had the same catch-all; it was
closed in Week 8 (TP-W03).

\section{Closing the Loop -- Stock Results and Order State (Week 8)}
\label{sec:week8}

Weeks 6--7 built one direction of the pipeline: an order becomes an
\texttt{OrderPlaced} event, which Inventory Service reserves against Redis.
Week 8 builds the return direction -- Inventory Service telling Order
Service what happened, and Order Service acting on it -- which is what
actually lets an order leave \texttt{PendingStock}.

\subsection{Inventory Service's own Outbox -- a harder dual-write problem}

Order Service's Week 6 Outbox writes a business row and an outbox row to the
\emph{same} Postgres database in one transaction, so atomicity is free.
Inventory Service cannot do that: the business fact (stock was reserved) is
recorded in Redis by \texttt{reserve.lua}, and the outbox fact (tell Order
Service) must be recorded in Postgres -- two different data stores that
cannot share a transaction. Rather than accept a gap where a process crash
between the two writes silently drops the notification, Inventory Service
gets its own \texttt{outbox\_events} table (\texttt{inventory\_service}
schema) with one deliberate difference from Order Service's: the unique
index is on \texttt{OrderId}, not \texttt{Id}.

That difference is what makes the Lua script's \texttt{DUPLICATE} outcome
safe. \texttt{DUPLICATE} means a \emph{previous} delivery of the same
\texttt{OrderPlaced} message already reserved the stock in Redis -- so if
the consumer treated it as a no-op, a redelivered message would never
produce a \texttt{StockReserved} row, and that order would sit in
\texttt{PendingStock} forever despite the reservation having genuinely
succeeded. Instead, both \texttt{RESERVED} and \texttt{DUPLICATE} run the
same step in \texttt{OrderPlacedProcessor}: check whether an outbox row
for this \texttt{OrderId} already exists, and only insert if it doesn't. The
unique index turns a possible race between two redeliveries into a unique
violation, which is caught, rather than a duplicate row -- "ensure exists",
not "insert unconditionally". The Inventory Service \texttt{RabbitMqOutboxPublisher}
and \texttt{OutboxPublisherWorker} use the same design as Order Service's
Week 6 versions (raw \texttt{RabbitMQ.Client}, routed confirmation, 2s poll
interval).

\subsection{Order Service: consuming the result}

\texttt{StockResultConsumer} consumes two queues, \texttt{StockReserved} and
\texttt{StockRejected}. Each queue has its own dead-letter queue. Both queues
share one handler, which calls \texttt{StockResultProcessor} with the target
state. The processor works in this order:

\begin{enumerate}
  \item Check the Inbox. If the \texttt{MessageId} has already been
    processed, acknowledge and stop.
  \item Look up the order. If it does not exist, acknowledge and stop.
  \item If the order is already in the target state, or has moved past it on
    the happy path, record the Inbox row and treat the message as a no-op.
  \item Otherwise call \texttt{Order.TransitionTo} and add the Inbox row.
    Both are committed by one \texttt{SaveChangesAsync}.
\end{enumerate}

The message is acknowledged only after that commit. Failures are handled in
three ways:

\begin{itemize}
  \item \textbf{Conflicting result.} For example, \texttt{StockReserved} for
    a \texttt{Rejected} order. This is not transient, so it is dead-lettered
    at once.
  \item \textbf{Database error.} It is retried after 1, 2 and 4 seconds, then
    dead-lettered. Only a unique violation counts as a concurrent duplicate
    (TP-W01, TP-W03).
  \item \textbf{\texttt{OrderProcessed}.} The Process Worker's event is
    handled by \texttt{OrderProcessedConsumer}. It reuses the same processor
    with the target state \texttt{Completed}.
\end{itemize}

\subsection{Automated correctness validation}
\label{sec:validation}

\texttt{scripts/validate-correctness.ps1} checks the four inventory
invariants for one product after a run, with separate rules for C1 and C2
(\texttt{docs/validation.md}). It takes the configuration, product id and
initial stock as parameters, so Weeks 13--14 can reuse it unmodified.

\paragraph{What the Week 8 code check found.} The earlier validator gave
false passes. It could not validate C1 at all, because it read Redis and the
asynchronous \texttt{orders} table while C1 lives in
\texttt{order\_service.inventory} and \texttt{baseline\_orders}. Two of its
four checks could never fail. Invariant 3 counted duplicate order
\emph{primary keys}, which the primary key forbids. Invariant 4 counted
duplicate \texttt{MessageId}s in \texttt{processed\_messages}, which its unique
index forbids. On a fixture where 3 units were taken for 2 reserved orders
(a double deduction), the old validator printed \texttt{PASS} for all four
invariants and exited 0. The validator results shown in earlier drafts of
this report were produced by that version, and their invariant 3 and 4
lines are therefore not evidence.

\paragraph{Rules.} For C1: stock $\ge 0$; Confirmed decisions $\le$ initial;
units taken (initial $-$ stock) $=$ Confirmed decisions, so every deduction
has exactly one logged decision. Invariant 4 is reported \texttt{NOT
APPLICABLE} with its reason, because C1 has no broker messages. For C2: Redis
stock $\ge 0$; both Redis reservations and successful orders $\le$ initial.
The Redis reservation set and the successful orders must be exactly the same
order ids (one reservation per order). Units taken must equal distinct
reserved orders (no double deduction), and the Inbox \texttt{MessageId}
uniqueness must exist in both services. A run with no data, or with a reserved
order still \texttt{PendingStock}, is \texttt{INCONCLUSIVE}; an unreachable

\section{Reliability and Idempotency Layer (Week 9)}
\label{sec:week9}

\subsection{Message delivery semantics}

RabbitMQ delivers at-least-once. A message is removed from its queue only
when the consumer acknowledges it. If the consumer dies first, or its
connection drops, the broker delivers the same message again. Duplicates
therefore cannot be avoided at the transport. The system's goal is the next
best thing: every side effect happens effectively once, however many times
a message arrives.

Two kinds of duplicate have to be absorbed, by two different layers.

\begin{itemize}
  \item \textbf{Transport duplicates.} The same broker message (same
    \texttt{MessageId}) arrives again, for example after a crash or a
    connection loss. The \emph{Inbox} absorbs it. Each service has a
    \texttt{processed\_messages} table with a unique index on
    \texttt{MessageId}, created by the \texttt{AddProcessedMessages}
    migration of each service.
  \item \textbf{Business duplicates.} The same fact arrives under a
    \emph{new} \texttt{MessageId}. The reconciliation job does exactly this
    when it re-publishes \texttt{OrderPlaced}. The Inbox cannot see these,
    because the \texttt{MessageId} is new. Business rules absorb them
    instead:
    \begin{itemize}
      \item Redis's \texttt{processed:\{product\}} set makes the Lua script
        answer \texttt{DUPLICATE} for an order that already holds a unit;
      \item Inventory's result Outbox has one row per order id;
      \item Order Service treats a result for a state the order already
        has, or has passed, as a no-op.
    \end{itemize}
\end{itemize}

Table~\ref{tab:consumers} lists every consumer. Only a PostgreSQL unique
violation (23505) is treated as ``already processed''. Any other database
error is retried and then dead-lettered, so a failed write is never
acknowledged as done (Week 8, TP-W03).

\subsection{Idempotent consumer}

The correctness logic lives in two small classes that a test can drive
directly. \texttt{OrderPlacedProcessor} serves Inventory Service, and
\texttt{StockResultProcessor} serves both Order Service consumers. The
consumer classes around them only deserialize, retry, and acknowledge or
reject. Each processor works in this order:
\begin{enumerate}
  \item \textbf{Check the Inbox.} If the \texttt{MessageId} is recorded,
    report ``already processed'' and touch nothing. In Inventory Service
    this check runs before the Lua script, so an exact redelivery never
    reaches Redis.
  \item \textbf{Decide.}
    \begin{itemize}
      \item Inventory runs the Lua reservation.
      \item Order Service compares the order's state with the result. A
        result for the same or an earlier state on the happy path (for
        example a late \texttt{StockReserved} after \texttt{Completed}) is a
        no-op. A completion that arrives while the order is still
        \texttt{PendingStock} returns \texttt{NotYetApplicable}: it writes
        nothing and the consumer requeues it. Any other mismatch is a
        genuine conflict, which throws and is dead-lettered.
    \end{itemize}
  \item \textbf{Commit once.} The business change (Inventory's result
    Outbox row, or Order Service's new state) and the Inbox row are added
    to one \texttt{DbContext}. One \texttt{SaveChangesAsync} commits both,
    so either both happen or neither does.
  \item \textbf{Absorb the race.} Two deliveries can pass step 1 together.
    The unique index then rejects the second insert, and that unique
    violation, and only that one, is reported as ``already processed''.
\end{enumerate}

\texttt{Order.TransitionTo} has no self-loop for \texttt{Confirmed} or
\texttt{Rejected}. That is why the processor detects ``already in this
state'' itself. Otherwise a legitimate redelivery would throw the same
exception as a genuine conflict, and the two would be indistinguishable.

The local transaction was tested directly (TP-M01). With \texttt{INSERT} on
the Inbox revoked, the business write rolled back with it in both services,
the message was retried and then dead-lettered, and a replay applied it once.

\subsection{Acknowledgement strategy, proven with a real crash (Step 9.3)}

Every consumer follows the same rule (\texttt{docs/delivery-semantics.md}):

\begin{enumerate}
  \item Check the Inbox.
  \item Do the business step and insert the Inbox row in one local
    transaction.
  \item Acknowledge only after that transaction commits
    (\texttt{autoAck: false}).
\end{enumerate}

The dangerous moment is between the commit and the ack. If the process dies
there, the work is done but the broker still holds the message, so it
delivers it again.

\paragraph{What the code check found.} An earlier draft of this section
described a manual crash test. Its output was never saved, and it killed
Inventory Service \emph{before} it processed the message. That shows an
unprocessed message is redelivered. It does not test the case this step is
about: a crash \emph{after} the commit.

\paragraph{Fault injection.} Each of the four consumers now calls a fault-injection hook,
\texttt{CrashBeforeAckIfTargeted}, between its commit and its
ack:

\begin{itemize}
  \item Inventory's \texttt{OrderPlaced} consumer;
  \item Order Service's stock-result consumer;
  \item Order Service's \texttt{OrderProcessed} consumer;
  \item the Process Worker.
\end{itemize}

The call does nothing unless two test settings name the consumer and one
correlation id. Neither setting is present in any \texttt{appsettings.json}.
When both match, the process kills itself (\texttt{Process.Kill}), with no
graceful shutdown that could still acknowledge the message. Targeting one
correlation id leaves all other traffic untouched.

\paragraph{Process Worker.} The Process Worker has no database and therefore
no Inbox. Its only effect is publishing \texttt{OrderProcessed} with
\texttt{MessageId} equal to the order id. A redelivered
\texttt{StockReserved} makes it publish the same message again, and Order
Service's Inbox absorbs the copy.

\subsection{Concurrent duplicates and out-of-order completion (TP-M02)}

Three ordering risks remain once each consumer has an Inbox:
\begin{itemize}
  \item many copies of one message arriving at the same moment;
  \item the same business fact arriving again under a new
    \texttt{MessageId} (the reconciliation job does exactly this);
  \item a completion arriving before the result it depends on.
\end{itemize}

Section~\ref{sec:design-decisions}. The Process Worker and Order Service both

\texttt{OrderProcessedConsumer} then:
\begin{enumerate}
  \item republishes the message onto a delayed retry queue
    (\texttt{OrderProcessed.retry.1}--\texttt{3}, with TTLs of 2, 4 and
    8\,s, each bound to the dead-letter exchange);
  \item uses a channel with publisher confirms for that publish;
  \item acknowledges the original only after the confirm.
\end{enumerate}
Each retry queue dead-letters back onto \texttt{OrderProcessed}, and the
completion is applied once the order is \texttt{Confirmed}. If it is still
early after three requeues, it goes to the DLQ instead of waiting forever.
The 1, 2, 4\,s in-process retry for database errors is unchanged and kept
separate.

\section{Failure Handling and Recovery (Week 10)}
\label{sec:week10}

Weeks 6--9 made every individual message idempotent. Week 10 handles the
failures \emph{around} that idempotency: a handler that throws, a message
nobody can ever process, and an order that slips through every other net.
The mechanisms are bounded retry, a dead-letter queue per service, and a
reconciliation safety net. The chapter ends with the failure model: which
failures are verified, which are only designed, and which are not supported.
Following the teacher brief, payment failure, compensation, Redis Cluster,
RabbitMQ Cluster, PostgreSQL replication and multi-region deployment are out
of scope.

\subsection{Classify, then retry a bounded number of times}

A failure is classified before it is retried
(\texttt{docs/failure-handling.md}). There are three classes:
\begin{itemize}
  \item \textbf{Transient}, such as a brief database outage or a missing
    queue: retried.
  \item \textbf{Permanent (poison)}: never retried.
  \item \textbf{Business rejection}, a genuine state conflict: a decision,
    not something to retry.
\end{itemize}
Retry is implemented directly in each of the four consumers. These are
Inventory's \texttt{OrderPlacedConsumer}, Order Service's
\texttt{StockResultConsumer} and \texttt{OrderProcessedConsumer}, and the
Process Worker's \texttt{StockReservedConsumer}. ABP's RabbitMQ event bus is
not used (Week 6).

All four use the same in-process ladder as \texttt{OutboxPublisherWorker}:
four attempts, with 1\,s, 2\,s and 4\,s waits. After the fourth attempt the
consumer logs an error and nacks the message without requeue, so the message
is dead-lettered with its body intact rather than looping forever. Retrying
the whole processing call is safe because every processor is idempotent
(Week 9): a retry that follows an attempt which had in fact succeeded sees
the Inbox row and returns cleanly. Only a PostgreSQL unique violation (23505)
counts as ``a concurrent duplicate already recorded this''. Every other
database error is retried and then dead-lettered.

The two non-transient classes skip the ladder entirely:
\begin{itemize}
  \item \textbf{Business rejection.} \texttt{InvalidOrderStateTransitionException}
    is deterministic, so retrying it would reproduce the same conflict four
    times. It is nacked to the DLQ at once.
  \item \textbf{Permanent (poison).} Each consumer validates the message's
    identity fields straight after deserialization, before any Redis, SQL or
    Inbox work. An empty \texttt{MessageId}, \texttt{OrderId} or
    \texttt{ProductId} is permanent (\texttt{OrderProcessed} carries no
    \texttt{ProductId}). So is an \texttt{OrderPlaced} whose
    \texttt{Quantity} is not 1, because the reservation scope is exactly one
    unit. Such a message is nacked without requeue after one attempt, and
    the consumer logs \texttt{Invalid <Event> message: <Field> is empty;
    routing to DLQ}.
\end{itemize}

The validation fixed a real bug, not just a gap. Before it, an
\texttt{OrderPlaced} with an empty \texttt{MessageId} was processed as if it
were real. The Inbox then recorded \texttt{Guid.Empty}, so a
\emph{second, different} invalid message was wrongly skipped as ``already
processed''.

\subsection{A dead-letter queue per service, and replay}

Every main queue declares \texttt{x-dead-letter-exchange=flashsale.dlx}.
That exchange routes each dead letter into exactly one service's DLQ:
\begin{itemize}
  \item \texttt{OrderPlaced.dlq} for Inventory;
  \item \texttt{StockReserved.dlq}, \texttt{StockRejected.dlq} and
    \texttt{OrderProcessed.dlq} for Order Service;
  \item \texttt{ProcessWorker.StockReserved.dlq} for the Worker.
\end{itemize}
The Worker's queue also rewrites the dead-letter routing key.
\texttt{flashsale.dlx} is a direct exchange shared by all three services.
Without the rewritten key, a Worker dead letter (original key
\texttt{StockReserved}) would be copied into Order Service's
\texttt{StockReserved.dlq} as well. The rewrite keeps each DLQ limited to its
own service's failures.

A DLQ repairs nothing by itself, so it has a documented owner and replay
procedure:
\begin{enumerate}
  \item Inspect the dead letter. Its \texttt{x-death} header names the source
    queue and the reason.
  \item Fix the root cause.
  \item Republish the message unchanged, so it keeps the same
    \texttt{MessageId}.
\end{enumerate}
The Inbox, and \texttt{reserve.lua}'s \texttt{DUPLICATE} answer, make the
replay apply exactly once.

\paragraph{Verification (TP-F01).} \texttt{scripts/verify-failures.ps1}
runs all three services on a throwaway broker and Redis. For each of the four
consumers it checks four things:
\begin{itemize}
  \item \textbf{Transient fault.} A revoked Inbox \texttt{INSERT}, or a
    deleted queue for the Worker, is restored inside the window. The message
    is applied once and nothing is dead-lettered.
  \item \textbf{Exhausted retries.} A fault that outlasts the ladder produces
    exactly four attempts, about 1\,s, 2\,s and 4\,s apart according to the
    log timestamps. The message is then in that service's DLQ, with
    \texttt{x-death} reason \texttt{rejected}. The main queue is empty and
    every other DLQ is unchanged.
  \item \textbf{Poison.} Malformed JSON, an empty \texttt{MessageId} (two
    different such messages) and \texttt{Quantity}~=~2 are each
    dead-lettered after one attempt. None leaves an Inbox row or a Redis
    effect.
  \item \textbf{Replay.} The dead letter, republished unchanged, applies
    exactly once.
\end{itemize}

The fresh-clone run passed all 74 checks
(\texttt{tests/evidence/20261011T084521Z-failures.log}). A negative control
disabled the Inventory empty-\texttt{MessageId} check. Five checks then
failed and the script exited 1
(saved alongside it as \texttt{...-failures-negative.log}), which shows the
poison checks have teeth. The Week 9 regressions still pass on the same
clone: TP-M01 34/34, TP-M02 44/44, and the workflow and stock-result
verifiers.

\subsection{Reconciliation: stuck orders, a bound and an alert}
\label{sec:reconciliation}

Retries and the DLQ deal with \emph{messages}. Reconciliation is the safety
net for \emph{orders}: it finds an order that is still
\texttt{PendingStock} long after it should have been answered, and acts in a
bounded, visible way. It does not replace the Outbox, retry or the DLQ, and
it never changes an order's state to hide a problem
(\texttt{docs/failure-handling.md}).

\paragraph{Detection and cadence.} \texttt{ReconciliationWorker} (Order
Service) polls on a configurable interval (30\,s by default). It looks for
orders still \texttt{PendingStock} whose request was accepted longer ago than
a configurable timeout (also 30\,s by default). For each one it inserts
a fresh \texttt{OrderPlaced} Outbox row, which re-runs the normal pipeline. It
acts on an order at most once per timeout window, so a stuck order is not
re-triggered on every poll.

\paragraph{The bound and the alert.} The attempt count comes from the order's
own \texttt{OrderPlaced} Outbox rows: the first row is the original delivery,
and every later row is one re-trigger. Because the count lives in the
database, it survives an Order Service restart. An order is given up only
when two things are both true: the count has reached \texttt{MaxAttempts}
(3), and the last re-trigger has had its full window to work. A given-up
order:
\begin{itemize}
  \item is no longer re-triggered;
  \item produces one Error log line naming the order, its attempts and its
    age;
  \item stays \texttt{PendingStock}, because no \texttt{Rejected} is invented;
  \item is counted in three Prometheus metrics: re-triggers, orders given
    up, and orders currently stuck.
\end{itemize}

\paragraph{Recovering a known outcome.} Before Week 10, a re-trigger often
could not recover anything. Suppose Inventory had already published a result
and Order Service lost it, for example because it was dead-lettered and the
DLQ was purged. Inventory then saw that a result row existed and wrote
nothing, so the order stayed stuck while being re-triggered forever. Now a
re-triggered \texttt{OrderPlaced} for an order whose result was already
published re-sends that \emph{same stored result}: the same payload and the
same \texttt{MessageId}. There is no second Lua deduction
(\texttt{reserve.lua} answers \texttt{DUPLICATE}) and no new row. Order
Service's Inbox applies the result once, or ignores it if it was already
applied. A reserved order therefore stays reserved and is never rewritten as
out of stock.

The operator procedure is in \texttt{docs/failure-handling.md}: inspect the
order, its Outbox rows and the DLQs; fix the cause; then replay the dead
letter unchanged. Stock is never reset and queues are never deleted as a
``repair''.

\paragraph{Verification (TP-F02).} \texttt{scripts/verify-reconciliation.ps1}
runs all three services with short timeouts (5\,s, a 2\,s poll, a bound of
3). It covers six cases:
\begin{itemize}
  \item \textbf{A, lost result.} A reserved order's \texttt{StockReserved} is
    dead-lettered and the DLQ purged. Reconciliation re-triggers it, and
    Inventory re-sends the stored result, whose \texttt{PublishedAt} is
    re-stamped after the purge. The order ends \texttt{Completed}, with one
    deduction, one result row and the \emph{original} result
    \texttt{MessageId}.
  \item \textbf{B, transient outage.} Inventory is stopped, three orders are
    placed, and only Inventory is restarted. All three drain to
    \texttt{Completed} with one deduction each, and none is
    \texttt{Rejected}.
  \item \textbf{C, permanent fault.} With Inventory kept down, the order is
    re-triggered exactly three times. The give-up Error is logged exactly
    once, and the metrics read 3 re-triggers, 1 given up and 1 stuck. The
    order stays \texttt{PendingStock}.
  \item \textbf{D, Order Service restart.} The restarted service resumes from
    the stored count. It stops at the bound and does not start again from
    zero.
  \item \textbf{E, no false positive.} A normally completed order is never
    re-triggered.
  \item \textbf{F, outcome preserved.} When Inventory returns, the given-up
    orders from C and D complete with exactly one result each. The stuck
    gauge returns to 0, and the stock is conserved: 20 units minus 7 orders
    leaves 13.
\end{itemize}

A fresh-clone run passed all 30 checks
(\texttt{tests/evidence/20261011T102304Z-reconciliation.log}). A negative control
removed the Inventory re-send. Case A then stayed \texttt{PendingStock} with
its result never re-sent, and the script exited 1.

\paragraph{Confirmed and Processing (after the review).} Reconciliation first
watched \texttt{PendingStock} only, so an order whose Process Worker copy of
\texttt{StockReserved}, start event or completion was lost stayed
\texttt{Confirmed} or \texttt{Processing} for ever. It now also selects those
orders once their confirmation is older than
\texttt{ProcessingStuckTimeoutSeconds} (300\,s by default, never shorter than
the \texttt{PendingStock} timeout, because the Worker's queue legitimately
holds confirmed orders after an overload). The same re-trigger recovers them:
Inventory re-sends its stored \texttt{StockReserved}, which also reaches the
Worker. Case G stops the Worker, lets an order be confirmed, purges the
Worker's copy and restarts the Worker; the order ends \texttt{Completed} with
one deduction, and all 35 checks pass
(\texttt{tests/evidence/20261023T142609Z-reconciliation.log}). With the new
selection removed, case G fails: the order stays \texttt{Confirmed}
(\texttt{tests/evidence/20261023T143020Z-reconciliation-negative-control.log}).

\section{Process Worker and Observability (Week 11)}
\label{sec:week11}

Week 11 adds the last component of the pipeline and the instrumentation the
experiments will read it through. It also closes the oldest open question in
this project: the \texttt{Confirmed} $\to$ \texttt{Processing} $\to$
\texttt{Completed} leg that \texttt{docs/order-state-machine.md} had refused
to specify since Week 1.

\subsection{The Process Worker, and what it settled about the state machine}

\texttt{FlashSale.ProcessWorker} is a third service: it consumes
\texttt{StockReserved}, waits a deterministic delay, and publishes
\texttt{OrderProcessed}. Per Proposal §3 it simulates downstream processing
only -- there is no payment step, no failure injection and no compensation
logic, all three being excluded by \texttt{docs/00-scope-lock.md}. The delay
is deterministic rather than randomised on purpose: with a fixed service
time, any variance Week 13/14 measure in end-to-end latency comes from
queueing and contention in the architecture, not from the simulator adding
noise of its own.

It consumes from its \emph{own} queue
(\texttt{ProcessWorker.StockReserved}), bound to the same exchange with the
same \texttt{StockReserved} routing key as Order Service's queue. A direct
exchange copies the message to every bound queue, so both services react to
the same event independently. Sharing one queue would have made them compete
for messages, and roughly half of all orders would never have been processed
at all.

\paragraph{The six named states in the code.} An earlier Week 11 draft
removed \texttt{Processing} and \texttt{ProcessingFailed}, because Order
Service only learned two facts after placement. The project then adopted the
teacher's six named states (Section~\ref{sec:order-state-machine}), and the
code now implements them.
\begin{itemize}
  \item \textbf{A real trigger for \texttt{Processing}.} When the Process
    Worker begins work on a reserved order, it publishes
    \texttt{OrderProcessingStarted} (routed, with publisher confirms). Its
    \texttt{MessageId} is derived from the order id: a name-based UUID that
    differs from the \texttt{OrderProcessed} id (\texttt{MessageId =
    OrderId}). This keeps the two events apart in the Inbox, and a replay
    still regenerates the same id.
  \item \textbf{A consumer like the others.} Order Service consumes the event
    on its own queue, with the Inbox, the 1/2/4\,s retry ladder, validation
    and a DLQ.
  \item \textbf{\texttt{ProcessingFailed} is declared but unreachable.} The
    Worker is success-only by design, so no event and no code path sets it.
    A unit test and a source scan prove this.
\end{itemize}

\paragraph{History, and events that arrive out of order.} Every transition
writes a row to \texttt{order\_status\_history}, in the same transaction as
the state change. The order's creation writes the first row. A duplicate or
stale event is a no-op and writes no row. The API's polling response returns
the history.

The Worker consumes \texttt{StockReserved} in parallel with Order Service, so
its events often arrive before the order is \texttt{Confirmed}. They are then
requeued on bounded delayed retry queues, never dropped. If the completion
arrives before the start event, Order Service applies \texttt{Confirmed}
$\to$ \texttt{Processing} $\to$ \texttt{Completed} in one transaction. It
marks the \texttt{Processing} row as implied, and the start event later
becomes a no-op.

The review found two defects in the first version:
\begin{itemize}
  \item The implied row took the Worker's start time. That time can be
    earlier than the moment Order Service recorded \texttt{Confirmed}, so the
    history sorted \texttt{Processing} before \texttt{Confirmed}.
  \item The two rows written together could be inserted in either order.
\end{itemize}
The fix has three parts:
\begin{itemize}
  \item The history is read by the identity column \texttt{Seq}, not by time.
  \item The implied row's time is the later of the Worker's start time and
    the confirmation time.
  \item The implied path saves the \texttt{Processing} row and the
    \texttt{Completed} row in two steps inside one transaction, so their
    order is fixed and the change stays atomic.
\end{itemize}
A completion without a start time, such as one published by an older Worker,
uses the time it is applied, instead of the year 0001.

\paragraph{Verification (TP-P02).} The unit tests (90 at Week~11) cover:
\begin{itemize}
  \item the transition table;
  \item every 5-event sequence over the three Worker-facing events, 150 in
    total, each ending \texttt{Completed} with the four-step history;
  \item the clamped, kept and missing start times;
  \item the \texttt{Seq} order.
\end{itemize}
\texttt{scripts/verify-processing.ps1} runs all three services and covers
these cases:
\begin{itemize}
  \item normal orders by either legal path;
  \item a deterministic direct path, with the derived start id;
  \item duplicates, which change nothing;
  \item the late start event, which gives an implied row clamped to the
    confirmation time, then a no-op;
  \item 10 orders on the implied path, all in \texttt{Seq} order;
  \item Worker events while \texttt{PendingStock}, which are requeued and
    then applied;
  \item no \texttt{ProcessingFailed} anywhere;
  \item a poison start event, which goes to its DLQ.
\end{itemize}
The fresh-clone run passed all 41 checks
(\texttt{tests/evidence/20261013T145229Z-processing.log}). A negative control that writes the implied row
as not implied fails two checks, and the script exits 1.

\paragraph{Idempotency with no database.} The Process Worker is the only
service here with no persistent store, and deliberately so: it holds no
business state, so there is no local write that a publish could disagree
with, and therefore no dual-write problem and no need for an Outbox -- the
reasoning that forced Inventory Service to add one in Week 8 simply does not
apply. Step 11.1's requirement that it ``use \texttt{order\_id} as its own
idempotency key'' is met by deriving the published message's
\texttt{MessageId} from the order id (they are set equal) instead of minting
a fresh one per hop as every other event does. A redelivered
\texttt{StockReserved} therefore regenerates an \texttt{OrderProcessed}
with the same \texttt{MessageId}, which Order Service's Week 9 Inbox recognises
and drops (only its start time can differ): the idempotency key travels in the message rather than living in a
store.

\paragraph{A restart defect found and fixed.} The code check found that a
\emph{graceful} shutdown of the Worker (Ctrl+C, or SIGTERM from
\texttt{docker stop}) dead-lettered accepted work. Stopping the host cancels
the processing delay. The cancellation was caught as a failed attempt, the
retry wait then threw again, and the message was nacked to the DLQ. The
broker had already pushed every queued message to the Worker, so each of
those failed the same way. A throwaway prototype with 10 queued orders
dead-lettered 9 of them on one Ctrl+C. Now a cancellation caused by
shutdown is not a failed attempt. The message is left unacknowledged, so
the closing channel returns it to the queue, and one Information line names
the order. Real failures still take the 1/2/4\,s ladder to the DLQ.

\paragraph{Verification (TP-P01).} \texttt{scripts/verify-worker.ps1} runs
all three services on a throwaway broker and Redis
(\texttt{docs/process-worker.md}). It covers seven cases:
\begin{itemize}
  \item \textbf{Deterministic success.} With a 500\,ms delay, 5 orders
    complete. Each Worker duration is at least 500\,ms; the measured values
    were 517--643\,ms. Each applied completion has
    \texttt{MessageId = OrderId}.
  \item \textbf{Replay with the same identity, a duplicate with a new
    \texttt{MessageId}, and 5 concurrent copies.} The Worker repeats the
    work, and its attempt counter rises by the number of copies. Order
    Service still has one completion Inbox row, an unchanged
    \texttt{CompletedAt}, and no dead letter. Attempts and applied results
    are counted separately.
  \item \textbf{Graceful restart (a real Ctrl+C) and a crash.} Each restart
    happens with 5 orders in flight. The DLQ stays empty and the Worker logs
    no DLQ routing or error. After the restart, all 5 orders complete with
    one applied completion each.
  \item \textbf{Reordering.} A completion that arrives while the order is
    still \texttt{PendingStock} is requeued, not dead-lettered. It is applied
    exactly once after the stock result, with
    \texttt{ConfirmedOrRejectedAt} $\le$ \texttt{CompletedAt}. A late stock
    result after completion is a no-op.
\end{itemize}

The fresh-clone run passed all 51 checks
(\texttt{tests/evidence/20261011T160720Z-worker.log}). With the shutdown fix reverted,
the Worker logged 5 DLQ routings and 5 errors during shutdown, and the
script exited 1. The dead-letter count alone was not a reliable signal: the
reverted Worker's rejections sometimes reached the broker after the channel
had closed, and those messages were requeued anyway. So the check reads what
the Worker did, not only where the messages ended up.

\paragraph{A test defect found in Week 11.} A later fresh-clone run failed the
graceful-restart case although the Worker was correct. The cause was
Windows: a script started from Git Bash or a background task runs with
Ctrl+C ignored, and the Worker inherited that. The test's Ctrl+C call then
succeeded, but no Ctrl+C reached the Worker. The same run exposed a second
defect: the check for the Worker's shutdown line searched the whole log file,
so a line from an earlier run made it pass. Now the script turns Ctrl+C back
on before it starts the Worker. It proves delivery from the Worker's own
``Application is shutting down'' line, and it reads only the log lines
written after the Ctrl+C. Started from Git Bash, the fixed script passed all
51 checks twice, and then again from a fresh clone on a fresh database
(\texttt{tests/evidence/20261014T090016Z-worker.log}). Without the Ctrl+C fix
it fails the delivery check, the exit check and the shutdown-line check, and
exits 1.

\subsection{Correlation IDs across three services (Step 11.2)}

Each event now carries a \texttt{CorrelationId}, copied unchanged at every
hop. That invariance distinguishes it from the two identifiers already in the
contract: \texttt{MessageId} is regenerated at every hop (each consumer needs
its own Inbox key), and \texttt{OrderId} only exists once an order does,
whereas a correlation id identifies the \emph{request}.

Order Service does not mint the value. ABP's own
\texttt{app.UseCorrelationId()} middleware was already populating
\texttt{ICorrelationIdProvider} from the caller's \texttt{X-Correlation-Id}
header (generating one per request when absent), and
\texttt{app.UseAbp}\allowbreak\texttt{SerilogEnrichers()} was already stamping that value onto
every log line written during the request. Generating a second id in the
controller would have made the HTTP log lines and the order row disagree
about what the request is called -- the precise failure this step exists to
prevent -- so the controller takes ABP's value and carries it onto the order
and every event that follows. Across the message hops, where no HTTP
middleware exists, each consumer re-establishes it with
\texttt{LogContext.PushProperty}, which flows through the awaits into
everything that logs downstream of it.

Every log line also carries a \texttt{Service} property, so one search over
the three JSON logs shows which service wrote each line. The Process Worker's
\texttt{Received} line now names the incoming \texttt{MessageId}, so the
\texttt{StockReserved} it consumed can be matched to the one Order Service
consumed.

\paragraph{Verification (TP-P03).} \texttt{scripts/trace-order.ps1} places
three orders, each with its own \texttt{X-Correlation-Id}:
\begin{itemize}
  \item one that completes;
  \item one that Inventory rejects;
  \item one that completes after a recovered fault, with Order Service's
    Inbox \texttt{INSERT} grant revoked for about 3\,s.
\end{itemize}
For each order it searches the three JSON logs for that one id and checks
that:
\begin{itemize}
  \item every expected hop is present, each line tagged with its service;
  \item the \texttt{MessageId}s link up: the id in each Outbox row is the id
    the next consumer logs;
  \item every stage timestamp is present and ordered (acceptance $\le$
    publication, and acceptance $\le$ decision $\le$ applied $\le$
    completion);
  \item the history, read by \texttt{Seq}, and the API's polling response
    agree.
\end{itemize}

The exported metrics fall into five groups:
\begin{itemize}
  \item \textbf{Business results.} \texttt{flashsale\_orders\_accepted\_total}
    counts orders, and only after the commit, so it can be compared with
    JMeter's request count. \texttt{flashsale\_orders\_outcome\_total\{outcome\}}
    counts state changes that were actually applied, never an idempotent
    no-op, so it cannot drift from the database under redelivery. Inventory's
    \texttt{flashsale\_stock\_decisions\_total\{outcome\}} has the values
    \texttt{reserved}, \texttt{rejected}, \texttt{not\_open} and
    \texttt{duplicate}. Each counts a business result, never an attempt.
  \item \textbf{Work attempts, kept apart from results.} The Worker's
    \texttt{flashsale\_orders\_processed\_total} and
    \texttt{flashsale\_process\_worker\_duration\_seconds} count every
    processing run, including replays. A replay therefore raises the attempt
    count but not the completion count.
  \item \textbf{Reliability.} All three consumers export
    \texttt{flashsale\_consumer\_retries\_total} and
    \texttt{flashsale\_consumer\_dead\_lettered\_total}, both labelled by
    consumer. The dead-letter counter also has a reason: \texttt{exhausted}, \texttt{invalid} or

    \texttt{flashsale\_consumer\_duplicates\_total\{consumer\}}, and Order
    adds \texttt{flashsale\_consumer\_requeued\_early\_total\{consumer\}}.
    The reconciliation metrics come from Week 10.
  \item \textbf{Backlog.} Order and Inventory export
    \texttt{flashsale\_outbox\_unpublished} and
    \texttt{flashsale\_outbox\_oldest\_unpublished\_age\_seconds}, refreshed on
    every publisher poll.
  \item \textbf{Resources.} The \texttt{prometheus-net} defaults give each
    process's CPU seconds and working set.
\end{itemize}
Labels hold only a few fixed values (consumer, outcome, reason). Order ids and
message ids stay in logs and database rows. A label per order would give one
series per order and overload Prometheus under the very load being measured.
Every labelled series is created at start-up, so a rate over a run that saw
no retries reads 0 and is never missing.

\paragraph{Verification (TP-P04).} \texttt{scripts/verify-metrics.ps1} reads
each service's \texttt{/metrics} before and after eight cases. It checks that
each case moved the expected series by the expected amount:
\begin{itemize}
  \item three normal orders: accepted, completed, reserved and Worker
    attempts each $+3$;
  \item a stock rejection: both rejection counters $+1$;
  \item a duplicate \texttt{StockReserved}: duplicates $+1$, and the
    confirmed count unchanged;
  \item a transient Inbox fault: retries $\ge 1$, no new dead letter, and the
    order completes;
  \item a poison message: \texttt{dead\_lettered\{invalid\}} $+1$;
  \item an early completion: requeued-early $\ge 1$;
  \item a paused broker: the Outbox gauges rise while it is paused and return
    to 0 afterwards;
  \item a Worker replay: attempts $+1$, but still one completion Inbox row.
\end{itemize}
It then checks that each service exports every metric the dictionary lists
for it (13, 8 and 7), and that no label value is an id. The fresh-clone run
passed all 17 checks (\texttt{tests/evidence/20261013T163454Z-metrics.log}). A negative control that stops counting
duplicate stock results fails case C (duplicates $+0$), and the script
exits 1.

\paragraph{Run-time collection and extraction (W11 milestone).} Several brief
metrics exist only while a run is in progress, and Prometheus does not hold
them: queue depth, the age of the oldest queued message, broker rates, Redis
latency, database connections and host load. Three additions make every metric
recordable and computable before the pilot:
\begin{itemize}
  \item \textbf{Message timestamps.} Every publish (both Outbox publishers,
    both Worker publishers and both delayed requeues) now stamps the AMQP
    \texttt{timestamp} property. RabbitMQ then reports the oldest queued
    message's age per queue, at the resolution of its statistics interval
    (5\,s by default). A unit test scans the source, so a future publisher
    cannot forget the stamp. TP-P06 checks all six paths on a live broker.
  \item \textbf{A run-time collector}
    (\texttt{scripts/collect-run-metrics.ps1}). Every 5\,s it appends the
    queue counts and ages, the broker rates, the Redis Lua call totals, the
    connections per service account, every service metric, and host CPU and
    memory to one long-format CSV. A source that fails is recorded as
    \texttt{unavailable}, never as 0, and the other sources keep sampling.
    One sample takes about 4\,s on the local host, so 5\,s is the shortest
    usable interval. TP-P07 checks it with Inventory stopped (the backlog
    grows) and Redis stopped (its rows become \texttt{unavailable}).
  \item \textbf{An extraction script}
    (\texttt{scripts/extract-run-metrics.ps1}). It turns one run's JTL,
    database rows and collected samples into the numbers the Results tables
    ask for. Percentiles use the nearest-rank method. Negative and missing
    stage intervals are counted, never hidden. Counter increases survive a
    restart, because each series is handled on its own. Drain time waits for
    the queues, the Outbox gauges and the run's own pending orders to reach
    0. Recovery time stays \texttt{unavailable} until the pilot sets its
    thresholds. TP-P08 checks it against hand-computed answers, including a
    counter reset, a negative interval and a late completion, and against a
    real run.
\end{itemize}
Writing these checks found four defects that a single test run would have
hidden: a seven-hour shift in every time window (this machine is UTC+7, the
EC2 host is not), a false 0 from a broker statistic that had not arrived yet,
a counter sum that over-counted after one service restarted, and a pending
count that included older orders and so could never drain. The time window,
the counter reset and the older orders each have a known-answer check whose
negative control fails as designed. The broker statistic is now recorded as
\texttt{unavailable} until it arrives. That path is shown in the code and the
test design, not by a separate test. From a fresh clone on a fresh database,
TP-P06, TP-P07 and TP-P08 passed 40, 15 and 35 checks, and every earlier
runtime verifier still passed
(\texttt{tests/evidence/20261014T140055Z-message-timestamps.log},
\texttt{20261014T140223Z-run-collector.log},
\texttt{20261014T140415Z-extract.log}).

reconstructed from the per-order timestamp schema below. A Prometheus
histogram of the same quantity would be a third, bucketed copy that disagrees
with both at the tail -- which is exactly where this project's research
question lives.

Two of these boundaries are not where a reader might assume, and both are
declared rather than corrected:
\begin{itemize}
  \item \texttt{RequestAcceptedAt} is set before the commit, so the order
    only becomes durable slightly later.
  \item \texttt{PublishedAt} is the time the confirmed publish was
    \emph{sent}. Until the review after Week~12 it was the time the confirm
    came back; since the broker delivers before it confirms, 714 of 773
    publish-to-decision intervals in the first TP-L04 run were negative.
    With the send time there were none in the following runs. A negative
    interval would still be reported as an anomaly, never clamped to zero,
    and a missing value is reported as missing, never as 0.
\end{itemize}
Publication time is read from the order's own Outbox row, joined by order id,
and is not copied onto \texttt{orders}. Copying it would add a second write to
the publish path of the very system whose throughput is being measured.

\paragraph{Replays after completion.} When a \texttt{StockReserved} for an
order that has already completed is delivered again, the two consumers
behave differently, and both are correct:
\begin{itemize}
  \item The Process Worker has no store, so it does the work again and
    republishes \texttt{OrderProcessed} with the same message id. Order
    Service's Inbox recognises that id, so the completion is not applied
    twice. TP-P04 case H measures this: the Worker's attempt counter rises by
    one, and the order still has one completion Inbox row.
  \item Order Service's own consumer treats a copy with the same message id
    as a duplicate (TP-P04 case C: duplicates $+1$, confirmed count
    unchanged). A stock result with a new message id, or one arriving after
    \texttt{Completed}, is a no-op, because the order has already moved past
    \texttt{Confirmed} (TP-M02). Since Week~9 neither case is dead-lettered. A dead letter is kept
    for poison messages and exhausted retries, and each service's dead
    letters stay in its own DLQ (TP-F01).
\end{itemize}

\section{Load Shedding}
\label{sec:load-shedding}

C3 adds three limits in front of the parts that cost real work, as brief
§4 asks: rate limiting at Nginx, concurrency limiting in the application and
bounded queues in RabbitMQ. A new request is refused early with a response code
that means ``too busy''. Every limit is off by default, so C2 behaves exactly
as before until a C3 configuration switches the limits on. The design is in
\texttt{docs/load-shedding.md}; Figure~\ref{fig:load-shedding-layers} shows
where each layer refuses work.

\paragraph{Nginx.} \texttt{infra/nginx.conf} is a reverse proxy to Order
Service. Its upstream, rate and burst come from the environment. Only
\texttt{POST /api/orders} is limited, in any letter case and with or without a
trailing slash: a \texttt{map} on the method and path gives every other request
an empty key, which \texttt{limit\_req} ignores, so status polling is never
refused. The key is the client IP, which acts as one global
bucket because JMeter runs from one machine.

\paragraph{Admission.} Order Service holds a zero-wait semaphore whose size is
\texttt{Admission:\allowbreak MaxConcurrent\allowbreak NewOrders}. The check sits after the
idempotency lookup and before any database write. A retry of an accepted order
therefore always gets its original order back, even when the gate is full, and a
refused order leaves no row and no Outbox event. The slot is released in a
\texttt{finally} block, so an exception or a cancelled request cannot leak it.

\paragraph{Backlog bound.} A bounded queue alone does not bound admission:
when a queue is full or the broker is down, accepted orders wait in the
Outbox, which could grow without limit. Order Service therefore also refuses a
new order (503, \texttt{reason=backlog}) when the unpublished Outbox has
reached \texttt{Admission:\allowbreak MaxOutboxBacklog}. The check runs after
the idempotency lookup and before the concurrency gate. The backlog is not
counted per request: the Outbox publisher measures it on every poll, and each
order accepted since that measurement is added at once. The bound therefore
holds even while a poll is stuck retrying an unavailable broker. It can be
overshot only by requests that pass the check at the same moment, which the
concurrency gate caps.

\paragraph{Bounded queues.} A RabbitMQ policy with a
\texttt{max-length} and the overflow mode \texttt{reject-publish} bounds the six main input queues and never
the retry or dead-letter queues. It is set and removed at run time by
\texttt{scripts/set-queue-bounds.ps1}, with no change to any queue declaration.
A publish to a full queue is nacked; the publisher's mandatory publish with
confirms (Section~\ref{sec:workflow}) leaves the Outbox row unpublished, and it
is retried until the queue has room. Every consumer takes at most 20
unacknowledged messages (a prefetch, added after the review), so the bound
covers real work; without it the Process Worker took its whole backlog as
unacknowledged messages, which \texttt{max-length} does not count.

\paragraph{In-flight bound (after the review).} The Outbox bound protects only
the first hop. Order Service therefore also refuses a new order (503,
\texttt{reason=inflight}) while \texttt{Admission:\allowbreak MaxInFlightOrders}
orders are still unfinished anywhere in the pipeline. The count is estimated
the same way as the backlog (a measurement about once a second, plus every
order accepted since) and is only measured while the bound is on, so C2 pays
nothing. Section~\ref{sec:review-fixes} explains why it was needed.

\paragraph{Verification.} Test case TP-L01
(\texttt{scripts/verify-load-shedding.ps1}) passed 18 of 18 checks on local
services:
\begin{itemize}
  \item \textbf{Gateway}, at 5 requests per second: 40 rapid POSTs gave 4
    accepted and 36 refused with 429. Ten more POSTs each to
    \texttt{/api/orders/} and \texttt{/API/orders} were all refused, since
    they share the same limit. No refused key has an order row, and 15 polls
    through Nginx were never refused.
  \item \textbf{Admission}, with 2 slots held for 1.5\,s: 10 parallel POSTs
    gave 2 accepted and 8 refused with 503 and \texttt{Retry-After}. The
    rejection counter rose by exactly 8, no refused key has an order row, and
    a replay of an accepted key returned 200 with the original order while the
    gate was full.
  \item \textbf{Bounded queue}, at a length of 3 with Inventory stopped: all 8
    orders were accepted, \texttt{OrderPlaced} held 3, and the Outbox held the
    other 5. After Inventory started, the Outbox drained to 0, every order

  \item \textbf{C2 unchanged}: with every limit off, 8 orders were accepted and
    completed.
\end{itemize}
Each limit was then removed in turn (rate 10\,000 per second, admission off, no
queue policy), and each removal made its case fail, so the checks detect a
missing limit. Run against the earlier Nginx configuration, which limited only

The unit tests (91 at that point in Week~12) and the earlier runtime test
cases still pass.

Test case TP-L02 (the same script, 29 of 29 checks in total) covers the

\subsection{Overload, drain and recovery (preliminary, local)}

\paragraph{Scenario.} Test case TP-L04 drives the full C3 stack through Nginx
with a three-phase JMeter plan
(\texttt{tests/jmeter/overload-recovery.jmx}): 30\,s at 3 orders/s
(baseline), 60\,s at 60 orders/s (overload), and 60\,s back at 3 orders/s
(recovery). Every limit is on: Nginx at 20 requests/s with a burst of 1,
admission at 8 concurrent new orders and an Outbox backlog of 20, and a
queue bound of 5. These values are local and pre-pilot; the Week~13 pilot
fixes the official ones. The baseline rate is deliberately below the slowest
stage: the Process Worker spends a fixed 200\,ms per order, and the run
measured it at about 3.7 orders/s. At 5 orders/s, an earlier run showed its
in-flight backlog still growing during ``recovery'', so that phase could not
show a return to a stable state.

\paragraph{What is measured.} The Week~11 collector samples the queues, the
Outbox and the services during the run, and the extraction script turns them
into numbers. The \emph{backlog drain after overload} is the time from the end
of the overload phase until all queued work (both services' unpublished Outbox
rows and the main queues' ready and unacknowledged messages) is back at its
baseline level, while recovery load continues. The \emph{final drain} is the
time from the last submission until every queue, the Outbox and every pending
order are empty. The \emph{recovery time} runs from the start of the recovery
phase to the first 10\,s window whose requests are back in range: no refusals,
no errors, p95 at most 1\,s, and at least one accepted order per second. The
review after Week~12 tightened both the backlog and the recovery definition;
the earlier ones missed the Worker's backlog and could count a phase that
refused everything as recovered.

\paragraph{Preliminary observations (local PC, one run each).}
Table~\ref{tab:overload-local-ec2} compares three local runs and two EC2 runs.
The first local run (22 October) passed every check of the time: the 2,390
refusals logged by Nginx and the 832 counted by the admission metric matched
JMeter exactly, all 773 accepted orders completed with one unit of stock each,
and no service restarted. Its 3.9\,s backlog drain, however, missed the
Process Worker's backlog. Once every consumer set a prefetch and all queued
work was counted (second run), the real picture showed: Order Service accepted
about 13 orders/s during the overload while the Worker finishes about 3.7/s,
orders took about 40\,s from acceptance to completion, and the backlog took
105\,s to clear, failing the 60\,s target. The Worker's bounded queue also held
back Inventory's result to Order Service, so orders sat in
\texttt{PendingStock} for about 32\,s. With the in-flight bound at the
database baseline plus 30 (third run), Order Service refuses what the Worker
cannot finish (Figure~\ref{fig:overload-timeline}): 548 orders were accepted,
each completed in about 6\,s (p95 6.8\,s), the backlog cleared in 6.9\,s, and

\paragraph{Design.} Two instances, a backend (\texttt{m7i-flex.large}) and

forgotten. Every container image is pinned to the exact version the local

never leave it.

\texttt{terraform destroy}. The assistant only reads the account, using a
read-only identity for \texttt{terraform plan} and checks. It runs commands on
the two tagged instances through Systems Manager, and can create, change or
delete nothing.

\section{External Review after Week 12}
\label{sec:review-fixes}

An external review graded Weeks~1--12 strictly. Every finding below was
confirmed in the code or the saved data before it was fixed, and each fix has
a test that fails when the fix is removed.

\begin{itemize}
  \item \textbf{State regression.} The start and completion consumers use
    separate database contexts, so a late ``processing started'' event could
    write \texttt{Processing} over a \texttt{Completed} order. The order's
    state is now an optimistic-concurrency token: the late write matches no
    row, and the event is decided again from a fresh read and acknowledged as
    stale. A unit test runs the completion between the start event's read
    and its save, both with Entity Framework's exception and with the one ABP
    raises.
  \item \textbf{Hidden backlog and the in-flight bound.} No consumer limited
    its unacknowledged messages, so the queue bound did not cover the
    Worker's backlog, and the backlog measure missed it. Every consumer now
    has a prefetch of 20 (peak unacknowledged 252 before, 20 after), the
    measure counts all queued work, and the in-flight bound keeps the backlog
    small (Table~\ref{tab:overload-local-ec2}).
  \item \textbf{Measurement.} The extractor now selects a run's orders by
    their own Idempotency-Keys (773, where the time window found 771), keeps
    one interval row per order when reconciliation re-publishes, stops on any
    SQL error instead of reading it as 0, and counts recovery only in windows
    without refusals and with accepted throughput. Publish times are taken
    when a message is sent, which removed the negative publish-to-decision
    intervals. Negative controls ran the previous extractor on the same
    inputs (\texttt{tests/evidence/20261023T123738Z-extract-negative-controls.log}).
  \item \textbf{Throughput limits.} Each Outbox publisher slept 2\,s after
    every batch of 50, capping it below 25 events/s, and opened a channel,
    checked the routing and saved the row once per message. It now starts
    the next full batch at once and sends a batch on one channel, checking
    the routing once per event type and awaiting the confirms together; each
    message still needs its own confirm. 300 queued rows drained in 1.3\,s
    (at least 230 events/s); the old loop needed at least 10\,s, and the
    per-message channel alone 8.1\,s. The Process Worker handled one order at
    a time (about 3.7 orders/s); \texttt{Processing:MaxConcurrency} now lets
    several orders wait out the delay together. Its default stays 1, so
    earlier results keep their meaning, and a higher value is an experiment
    parameter.
  \item \textbf{Reconciliation} also recovers orders stuck in
    \texttt{Confirmed} or \texttt{Processing}
    (Section~\ref{sec:reconciliation}; the failure model is in
    Section~\ref{sec:failure-model}).
  \item \textbf{Wording.} Order submissions are reported apart from status
    polls; the report no longer says a retry is never refused (Nginx can
    answer 429 first), that every consumer has an Inbox (the stateless
    Worker relies on Order Service's), or that the validator cannot report a
    false pass.
\end{itemize}

\paragraph{Second pass.} The same review was then checked again finding by
finding (\texttt{docs/midterm-review-disposition.md}):
\begin{itemize}
  \item Both Outbox publishers claim their batch with
    \texttt{FOR UPDATE SKIP LOCKED} inside a transaction. Before, every
    Inventory replica read the same oldest rows and published them: with two
    replicas the broker received 800 messages for 400 rows. Now 2 or 4
    replicas publish each row exactly once (TP-L05,
    \texttt{scripts/verify-replicas.ps1}), so C4 measures scaling rather than
    duplication.
  \item The state race is also tested on PostgreSQL, with two connections
    held at a barrier: both save orders, duplicate starts and conflicting
    stock results. Four of the six cases fail when the concurrency token is
    removed.
  \item A crash between the Redis reservation and the PostgreSQL save is now
    injected (TP-M01 case 1b). The restarted consumer gets \texttt{DUPLICATE}
    and writes the missing result with no second deduction; a control that
    erases Redis's record of the order deducts twice and fails.
  \item On EC2 the Worker listened only on its own loopback (its
    \texttt{Urls} setting overrode the container's), so its metrics were never
    scraped there; the Compose file now overrides it. The queue policy and the
    collector work through \texttt{docker exec} with no published management
    port and no password on the command line. All three were checked on EC2
    on 24 October (Section~\ref{sec:ec2-deployment}).
  \item The extractor judges recovery latency on accepted responses only,
    needs submissions in every second of the window, never reads a missing
    backlog series as 0, and exits 2 with every database-derived value
    \texttt{unavailable} when a query fails after the first probe.
  \item Verifiers that switch reconciliation off now use
    \texttt{Reconciliation:Enabled}; the earlier one-hour timeout still
    re-sent orders left over from earlier runs in the shared test database.
\end{itemize}

\sloppy\paragraph{First local pilot.} C1 and C2 were offered the same steady load
on the development PC, one after the other on the same processes, with no
load-shedding limit and the Worker running 32 orders at a time
(\texttt{scripts/run-pilot-c1-c2.ps1}; raw data
\nolinkurl{tests/evidence/20261024T112852Z-pilot-c1-c2-50rps-*} and
\nolinkurl{tests/evidence/20261024T113202Z-pilot-c1-c2-200rps-*}). The
validator passed all four runs. At 50 requests/s both kept up: C1 answered in
17/84\,ms (p50/p95) with the decision, C2 accepted in 25/43\,ms and Inventory
decided about 1.8\,s later. At 200 requests/s C1 still decided about 161
orders/s but answered in about 1.1\,s (JMeter's threads then offered it only
160/s), while C2 accepted all 202/s in under 61\,ms (p95) but its one
Inventory consumer, which handles one message at a time, decided only about
71/s, so decisions fell a minute behind. This single-machine, one-run result
is preliminary; it names the bottleneck that C4 and the Week~13 EC2 pilot
must measure.\par\fussy

\section{Measurement Method}

The configurations are those of the brief:
\begin{itemize}
  \item \textbf{C0}, a naive read-then-write. It only shows the race
    condition and is not a baseline.
  \item \textbf{C1}, a synchronous PostgreSQL conditional atomic update. This
    is the main baseline.
  \item \textbf{C2}, the asynchronous pipeline: Redis Lua, RabbitMQ, Outbox,
    Inbox and retry.
  \item \textbf{C3}, C2 with rate limiting, concurrency limiting and bounded
    queues.
  \item \textbf{C4}, C3 with 1, 2 and 4 Inventory consumers on the same EC2
    host.
\end{itemize}
Every run uses the same JMeter plan, run from a separate machine, and the
same seeded stock (\texttt{scripts/reset-and-seed.ps1},
\texttt{scripts/warm-up.ps1}). After each run,
\texttt{scripts/validate-correctness.ps1} gives its correctness verdict. A
configuration that is fast but over-sells has not won anything, so no
performance number is reported without that verdict.

Each configuration runs 3--5 times under the same conditions. For every run,
latency is reported as p50, p95 and p99. A table cell gives the median of
those values across runs, followed by the spread (range) across runs, for
example ``412 (398--431)''. The number of runs is given in each caption.

Latency comes from two sources that are kept apart. JMeter measures what the
client sees. The stage timestamps (Section~\ref{sec:week11}) measure the
pipeline inside the system. Where the two disagree, the disagreement is a
result to report, not an error to reconcile away. API throughput and
business throughput are always reported separately, because an accepted
request is not a completed order.

Each table and figure names the run ids its numbers come from
(\texttt{experiments/RUN-ID/}). Unless a caption says otherwise, a table
shows the steady-load, one-hot-product workload. The other workload profiles
of the brief get the same tables in the appendix.
