This report presents the midterm progress of the project after Week~12 of the
15-week plan. The system takes flash-sale orders through an asynchronous
pipeline. An Order Service, built on .NET~10 and the ABP Framework, writes each
order and its \texttt{OrderPlaced} event in one PostgreSQL transaction
(Transactional Outbox). RabbitMQ carries the events, an Inventory Service
reserves stock atomically with a Redis Lua script, and a Process Worker
simulates downstream work.

The work planned for Weeks 1--12 is implemented: the six-state order model,
idempotent order intake, Outbox and Inbox, bounded retry and dead-letter
queues, stuck-order reconciliation, tracing and metrics, overload control at
the gateway, the application and the broker, and the required Terraform
deployment on AWS EC2 with JMeter on a separate machine. The automated
verifiers and the unit tests pass on the assessed code
(Section~\ref{sec:verification}); passing tests show the cases they cover,
not universal correctness. In one local overload run and one EC2 run on the
assessed code, the system refused excess load early, lost no accepted order,
and cleared its backlog in under 7 seconds. Open limitations are listed in Section~\ref{sec:limits}.

The comparison between the asynchronous design and the synchronous PostgreSQL
baseline, the experiments with extra Inventory consumers, and the official
repeated runs remain for Weeks 13--14. Of two throughput limits found during
the midterm review, the Outbox limit is removed and the Worker's is now a
declared experiment parameter.

\section{Introduction}
\subsection{Problem and research question}
A flash sale concentrates a sudden burst of orders on a few products with
limited stock. Many concurrent requests competing for one inventory record
cause lock contention and longer response times, and a non-atomic
check-then-update can sell more units than exist (over-selling)
\cite{kleppmann}. When the
request rate exceeds processing capacity, an unbounded system lets queues and
latency grow until it fails.

\textbf{Research question.} How does an event-driven design with atomic Redis
Lua reservation (configuration C2) compare with a synchronous PostgreSQL
atomic-update baseline (C1) in latency, throughput, overload behaviour and
complexity, and what do load shedding (C3) and extra Inventory consumers (C4)
change? C0, a naive read-then-write implementation, only demonstrates the race
condition.

\subsection{Objectives}
\begin{itemize}
  \item \textbf{Asynchronous processing:} accept an order, store it with its
    event in one transaction, and answer with the order ID while stock and
    downstream work continue through RabbitMQ.
  \item \textbf{Inventory consistency:} stock never negative, successful
    reservations never above the initial stock, at most one reservation per
    order, and no duplicate deduction from a duplicate message.
  \item \textbf{Load shedding and resilience:} refuse excess load early at the
    gateway, the application and the broker; retry transient failures a
    bounded number of times and dead-letter poison messages.
  \item \textbf{Observability and evaluation:} trace every order by
    correlation ID, order ID and message ID with its state history and stage
    timestamps, and measure the effect of each design choice.
\end{itemize}

\subsection{Scope}
Backend only; clients are simulated with Apache JMeter. All backend components
run on one AWS EC2 instance and JMeter on a separate one. Each order has
quantity~1. The Process Worker is deterministic and success-only, so the
declared \texttt{ProcessingFailed} state has no producer. Authentication,
payment, compensation and clustering are out of scope, as the brief states.

\section{System design}
\subsection{Architecture}
All three services are .NET~10 applications on the ABP Framework \cite{abp}.
A client posts an order through the Nginx gateway to the Order Service, which
writes the order and an \texttt{OrderPlaced} Outbox row in one transaction and
answers 201 immediately (Figure~\ref{fig:arch}). The Outbox publisher sends the
event to RabbitMQ with mandatory routing and publisher confirms \cite{richardson,
rmq-confirms}. The Inventory Service reserves one unit atomically with a Redis
Lua script \cite{redis-lua} and publishes \texttt{StockReserved} or
\texttt{StockRejected} through its own Outbox. The Order Service and the
Process Worker consume the result. The Order and Inventory consumers record
every message ID in an Inbox table in the same transaction as the business
change, so a redelivered message has no second effect. The stateless Worker
gives its events fixed message IDs, so Order Service's Inbox drops the
repeats.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{system-architecture}
\caption{System architecture and event flow.}
\label{fig:arch}
\end{figure}

Each service owns a schema in one PostgreSQL instance and connects with its
own database account; cross-schema access is denied. This was re-checked on
the local stack after the latest migrations (test case TP-E04, 64 of 64
checks).

\subsection{Order state model}
Orders follow the six states named in the brief (Figure~\ref{fig:states}). The
Worker's start event moves a confirmed order to \texttt{Processing} and its
completion event to \texttt{Completed}. If the completion arrives first, both
steps are applied together and the \texttt{Processing} step is recorded as
implied. Every transition is stored in an ordered status history.

\section{Week 12: overload control and deployment}
\subsection{Load shedding (C3)}
Four limits protect the system, all off by default so that C2 is unchanged
(Figure~\ref{fig:layers}). Nginx limits the rate of new orders and answers 429
\cite{nginx-limit}. The Order Service refuses a brand-new order before any
database write, with 503 and \texttt{Retry-After}, when its Outbox backlog is
full, when too many orders are still unfinished, or when its concurrency
slots are taken. RabbitMQ main queues are bounded \cite{rmq-maxlength}. Every
consumer takes at most 20 unacknowledged messages \cite{rmq-prefetch}, so the
bound covers real work, and a full queue only delays publication through the
Outbox. A retry of an accepted order is answered before any application
limit, but Nginx can still refuse it with 429, so clients retry with back-off
\cite{nygard}.

\centering
\includegraphics[width=\textwidth]{load-shedding-layers}
\caption{Where each load-shedding layer refuses work.}
\label{fig:layers}
\end{figure}

\subsection{Overload, drain and recovery}
A three-phase JMeter run \cite{jmeter} offers 3 orders/s for 30\,s, 60 orders/s
for 60\,s, then 3 orders/s for 60\,s, with every limit on
(Table~\ref{tab:overload}). Counting all queued work showed that the first
local run hid a backlog behind the Process Worker, which finishes about 3.7
orders/s. During the overload the Order Service accepted about 13 orders/s,
orders waited about 40\,s end to end, and the backlog took 105\,s to clear,
failing the 60\,s target. The new in-flight limit refuses what the Worker
cannot finish: fewer orders are accepted (548 instead of 808), but each
completes in about 6\,s and the backlog clears in 6.9\,s (4.5\,s in the repeat
run) (Figures~\ref{fig:before} and~\ref{fig:after}). The same plan on EC2 with
the assessed code accepted 582 orders, completed each in about 5.5\,s and
cleared the backlog in 6.2\,s; every refused key was checked and none left an
order.

\section{External review after Week 12}
\label{sec:review}
An external review graded Weeks 1--12 strictly. Every finding was confirmed
in the code or the saved data before it was fixed, and each fix was re-tested:
\begin{itemize}
  \item \textbf{State regression.} A late ``processing started'' event could
    move a \texttt{Completed} order back to \texttt{Processing}. The order
    state is now an optimistic-concurrency token; a late event re-reads and is
    acknowledged as stale. A unit test fails without the fix.
  \item \textbf{Hidden backlog.} No consumer limited its unacknowledged
    messages, so the Worker held its whole backlog outside the queue bound
    (peak 252 unacknowledged before, 20 after). The backlog measure now counts
    all queued work, and the in-flight limit keeps it small; its test fails
    without the limit.
  \item \textbf{Measurement.} The metric extractor now counts a run's orders
    by their own keys (773, where a time window found 771), stops on any SQL
    error instead of reading it as 0, and counts recovery only when nothing is
    refused. The publication time of an event used to be stamped after its
    broker confirm, so a fast Inventory decision could precede it: 714
    publish-to-decision intervals were negative. It is now the send time of
    the confirmed publish. Negative intervals are counted and reported, never
    set to zero; the run in Table~\ref{tab:overload} has none.
  \item \textbf{Reconciliation} now also recovers orders stuck in
    \texttt{Confirmed} or \texttt{Processing} (lost Worker work); its runtime
    test fails without the change.
  \item \textbf{Wording.} Statements that overclaimed were corrected, and
    order submissions are now reported apart from status polls.
  \item \textbf{Second pass.} The state race is also tested on PostgreSQL
    with two connections held at a barrier (both save orders, duplicate
    starts, conflicting stock results); four of the six cases fail without the
    concurrency token. A crash between the Redis reservation and the
    PostgreSQL save is now injected; the restarted consumer writes the missing
    result with no second deduction, and a control that erases Redis's record
    of the order deducts twice and fails. The Outbox publishers no longer
    sleep after a full batch. The EC2 Worker listened only on its own
    loopback, so its metrics were never scraped there; this is fixed, and the
    queue policy and the collector now work through \texttt{docker exec}
    without a published management port; all three were checked on EC2 on
    24 October. The extractor judges recovery
    latency on accepted responses only and has fixtures for all-429, all-503,
    too little throughput, a gap in the window, missing samples and a failed
    database query.
\end{itemize}

limit is now a declared experiment parameter (\texttt{Processing:MaxConcurrency},
default 1). Both were far below the brief's target of about 2,000 reservation
attempts per second, and C4 adds Inventory consumers although neither limit is
in Inventory, so the pilot reports stock-decision latency apart from
completion latency as the brief requires. Adding Inventory replicas (C4) also
adds Inventory Outbox publishers, which poll the same table, and the single
Order Outbox publisher and the Worker stay as they are, so consumer scaling
alone cannot remove an upstream or downstream ceiling; C4 is read against
the stock-decision latency, not completion.

\section{Limitations and threats to validity}
\label{sec:limits}
\begin{itemize}
  \item \textbf{One run per configuration.} Every number in
    Table~\ref{tab:overload} is a single run on one PC; no spread can be
    reported until the repeated runs of Week~14.
  \item \textbf{Development PC and one EC2 run.} The local runs share one
    machine between the load generator, the services and the broker. EC2 has
    one run on the assessed code (24 October, raw data archived); the earlier
    EC2 run of 22 October used the code from before the review and kept only
    its console summary
    (\nolinkurl{tests/evidence/20261022T163505Z-ec2-overload.log}).
  \item \textbf{Fixed downstream delay.} The Worker's 200\,ms delay is a
    stand-in for real work, so completion latency mostly measures this
    setting and the Worker's concurrency.
  \item \textbf{Redis persistence.} Reservation idempotency relies on Redis
    keeping its set of reserved orders. If Redis lost it, a reconciliation
    re-send could take a second unit for the same order (stock lost, never
    oversold). This failure is not injected.
  \item \textbf{Shared verifier database.} Verifiers reuse one throwaway
    PostgreSQL; rows from an interrupted run can disturb a later one. The
    reproduction guide starts from a fresh one.
  \item \textbf{Floating container tags in the verifiers.} The Compose files
    pin every image, but the verifiers' throwaway containers use tags such as
    \texttt{nginx:latest}; a later pull can change the versions above.
  \item \textbf{Windows-only verifiers and no continuous integration.} The
    verifiers are Windows PowerShell~5.1 scripts; the collector runs on Linux
    under PowerShell~7, but the verifiers have not.
  \item \textbf{Passing is not proof.} Each verifier checks the cases it
    names; most were also shown to fail on a deliberately broken variant, but
    none proves correctness for inputs it does not try.
\end{itemize}
